# 一、项目总体与任务背景

## Q1：你这个项目到底要解决什么问题？

**A：**

这个项目要解决的问题，不是单个算法好不好，而是“在 4v4 超视距 CAP 防御任务中，如何把预警粗信息、机载雷达接手、协同探测、协同跟踪、战术模板、分层决策、导弹发射、接力制导和再组织，真正串成一条能运行、能复盘、能统计、能验证的完整作战链”。

如果把任务拆开看，项目实际上解决了五类问题：

- 第一类问题是感知问题。预警机提供的是粗信息，存在误差和短时丢失，不能直接拿来火控。
- 第二类问题是执行问题。高层战术语义必须落到底层飞行动作，不能停留在“应该这样做”的口头层面。
- 第三类问题是协同问题。4 架飞机不是各打各的，而是要在预警、扫描、跟踪、发射和接力上形成协同闭环。
- 第四类问题是战术问题。必须把拖曳射击、钳形夹击、上下夹击、前后攻击、并排射击、规避、回转等战术经验形式化。
- 第五类问题是验证问题。必须证明前面这些设计不是写在文档里，而是在真实 4v4 仿真中确实起作用。

因此，这个项目本质上不是“做一个算法点”，而是做一个以 CAP 防御任务为背景、以战术规则模板为主线、以协同探测和分层决策为核心的系统级项目。

## Q2：为什么选 CAP 任务，而不是普通的空战对抗？

**A：**

因为 CAP 任务天然要求“持续防护”，这比一次性交战更能考验系统完整性。

普通对抗任务往往只强调一次攻击窗口，而 CAP 任务强调的是：

- 在责任区内持续巡逻；
- 依托预警与机载雷达保持态势覆盖；
- 对来袭目标实施拦截；
- 在交战后继续维持防御链，而不是打一轮就结束。

换句话说，CAP 任务不是“打一架”，而是“持续守住一片空域”。这就天然需要：

- 协同探测，而不是单机盲打；
- 稳定跟踪，而不是瞬时截获；
- 门禁与接力，而不是简单见敌即射；
- 模板切换与再组织，而不是固定脚本。

所以，CAP 比单轮攻击更适合验证一个系统是否真正具备完整作战链能力。

## Q3：项目的任务目标是什么？

**A：**

项目的任务目标可以概括成一句话：

**在 4v4 责任区防御场景下，利用协同探测、协同跟踪、战术规则模板和分层决策，使我方在不盲目前出的前提下完成对来袭敌机的拦截、压制和清场，并保持较高生存性。**

如果按原任务要求展开，主要包括以下约束：

- 我方以保护高价值目标为任务核心。
- 责任区大小约为 `200 km × 300 km`。
- 高度控制层约在 `7 km - 12 km`。
- 我方不以远距主动出击为目标，而以责任区防护为优先目标。
- 要求在任务时限内抑制敌方进入高风险区，并控制中风险区压力。
- 需要兼顾战果、生存性和持续作战能力。

## Q4：原需求设计文档和当前实现的核心关系是什么？

**A：**

原需求设计文档给出的是理想化目标和理论框架，当前实现则是面向可运行与可验证的工程化落地版本。

二者关系不是“完全一致”，而是“主线一致、落地方式有调整”。具体来说：

- 原需求强调完整理论链条，包括态势评估、威胁评估、意图识别、模板选择、机动参数决策。
- 当前实现保留了这条主线，但在在线主链上更强调风险区、控制距离节点、预警/雷达链路和模板规则。
- 原需求更像“理想化综合智能决策框架”。
- 当前实现更像“可运行的状态机 + 模板规则 + 感知闭环 + 低层动作控制”。

因此，答辩时最稳妥的说法不是“当前代码百分之百复现了原需求全部理想设计”，而是：

**项目已经把原需求的关键主线落成了可执行系统，其中协同探测、协同跟踪、模板组织、分层决策、门禁与接力制导已经形成完整主链；意图识别模块已接入并运行，但在当前正式样本中更多承担中后段语义解释作用。**

## Q4.1：如果专家追问“你一直在讲我方设计，那敌方在项目里是怎么实现的”，怎么回答？

**A：**

敌方在当前项目里不是静态陪跑对象，而是一个有独立场景约束、战术逻辑和动作执行链的对抗方。

可以把敌方实现拆成三层：

- 第一层是场景层，决定敌方初始编队、初始高度、来向、速度和预警状态；
- 第二层是战术层，决定敌方逼近、拉开、重组和再攻击的节奏；
- 第三层是动作层，决定敌方每一拍实际输出什么高层动作，再如何落到底层执行。

所以，答辩时不能把敌方说成“背景板”，更准确的说法是：

**敌方是用于制造真实对抗压力、验证我方方法链是否真的被触发和被迫工作的对抗体。**

## Q4.2：如果专家继续问“为什么你们必须把敌方也介绍清楚”，怎么回答？

**A：**

因为只有把敌方讲清楚，专家才会相信你的验证不是“对着一组没有反应的目标做演示”。

具体讲，敌方设计决定了三件事：

- 我方协同探测到底是在稳定环境还是受扰环境中工作；
- 我方模板和打断机制到底会不会真的被触发；
- 第六部分的战果到底是靠方法赢来的，还是靠场景太弱赢来的。

所以敌方实现不是旁枝，而是你整套验证可信度的重要组成部分。

最终交付的是一套可运行、可解释、可验证的 CAP 协同空战系统链，核心交付物包括：

因此，这个项目的交付单位是“系统链”，而不是单一模块。

# 二、总体架构与系统主链

## Q6：项目的总体技术路线是什么？

**A：**

总体路线可以概括为六步：

1. 明确 CAP 任务背景、责任区与风险区约束。
2. 建立飞机、导弹、火控雷达和电子对抗的底层模型。
3. 依托预警粗信息与机载雷达实现协同探测和协同跟踪。
4. 基于战术距离节点、风险区与几何态势实现战术模板组织。
5. 通过分层决策把阶段推进、模板选择、机动执行和参数修正连接起来。
6. 用三次正式 4v4 仿真验证整条作战链的有效性。

如果从系统主链角度表达，可以写成：

`任务约束 -> 感知链 -> 跟踪链 -> 模板链 -> 控制链 -> 武器链 -> 验证链`

## Q7：这个系统的总体架构怎么理解？

**A：**

可以把系统理解成五层结构：

- 第一层是任务层：定义责任区、靶眼、风险区、任务目标和约束。
- 第二层是物理层：提供飞机、导弹、雷达、对抗等底层运行能力。
- 第三层是协同感知层：负责从 AWACS 粗信息到机载雷达接手，再到稳定跟踪。
- 第四层是战术组织层：负责模板选择、角色分工、编队引导、节点推进。
- 第五层是综合验证层：负责把全过程量化成时间线、控制距离、门禁、接力、战果和安全边界。

项目的关键不是某一层有多复杂，而是这些层之间已经真正打通。

## Q8：项目的主状态机是什么？

**A：**

项目顶层 CAP 状态机是：

- `PATROL`
- `INTERCEPT`
- `ENGAGE`
- `EVADE`
- `RTB`

对应实现位于：

- `cap/cap_state_machine.py`

它的作用不是做底层动作控制，而是给系统一个全局任务状态语义。也就是说：

- `PATROL` 表示还在巡逻或保持责任区覆盖；
- `INTERCEPT` 表示已经进入接敌组织；
- `ENGAGE` 表示交战链正式打开；
- `EVADE` 表示导弹威胁或近距压力触发了规避优先；
- `RTB` 表示撤离返航。

专家如果问“打断机制有没有真实落点”，最直接的代码级回答就是：

**有，联队级打断的显式落点就是 `EVADE`。**

## Q9：为什么没有把整个系统写成一个统一的大优化器？

**A：**

因为 CAP 任务是高度事件驱动、状态离散明显、信息不完备而且需要在线实时响应的。当前项目更适合用“分层规则 + 阶段节点 + 几何求解 + 低层控制网络”的方式，而不是做一个一次性全局连续优化器。

原因主要有四点：

- 第一，敌方机动、预警丢失、导弹威胁都是突发性的，统一大优化器很难稳定实时重解。
- 第二，很多关键约束本身就是离散门禁，例如“是否稳定双机跟踪”“是否允许发射”“是否触发接力”。
- 第三，战术模板本身就是经验结构化表示，和状态机天然兼容。
- 第四，验证与复盘要求每一步可解释，规则树和阶段推进更容易说明因果链。

所以当前实现的重点不是追求形式上最优，而是追求链路稳定、逻辑清楚、结果可复盘。

## Q10：整个项目最核心的创新点是什么？

**A：**

可以概括成五点：

- 第一，把 CAP 任务背景下的多机协同作战链完整落地，而不是只做单点算法。
- 第二，提出并实现了“基于不确定性传播-协同闭环七层联动”的协同探测方法。
- 第三，把战术经验形式化成战术规则模板，并与低层动作链打通。
- 第四，构建了分层战术决策体系，使阶段、战术、机动、参数四层形成可执行闭环。
- 第五，把发射门禁、稳定跟踪和接力制导纳入同一条可量化的攻击链。

如果只能讲一句话，可以说：

**本项目的创新不在于单点模型极致最优，而在于把感知、跟踪、模板、决策、控制和武器链真正打通成了一套可运行的 CAP 协同空战系统。**

# 三、底层物理模型与执行链

## Q11：飞机六自由度模型在项目里到底是怎么用的？

**A：**

飞机六自由度模型不是在项目里从零手写积分器，而是依托 LAG 底层平台和 JSBSim 提供的飞行动力学承接。当前项目在这一层的工作重点，不是重复造一个积分器，而是把高层机动语义稳定地送入这个动力学底座。

也就是说，项目对六自由度模型的使用方式是：

1. 高层给出战术语义，例如转向、爬升、速度调整。
2. 中间层把语义离散成高度、航向、速度三元组。
3. 低层策略网络把三元组和当前飞行状态翻译成四维连续控制量。
4. JSBSim 使用这些控制量更新姿态、速度和位置状态。

所以在答辩中不能把这一层说成“我们重新建立了全套六自由度求解器”，更准确的说法是：

**我们基于成熟仿真平台承接六自由度动力学，并重点解决了高层战术意图如何稳定地驱动这一物理底座。**

## Q12：为什么这样做是合理的？

**A：**

因为本项目重点是 CAP 协同作战系统，而不是飞行动力学仿真器本身。只要底层动力学模型可信、接口稳定，上层更重要的问题是：

- 高层语义如何表达；
- 低层控制如何平滑；
- 动作能否稳定执行；
- 战术模板是否真的影响飞行轨迹。

当前实现把精力集中在这些真正影响任务成败的部分上，是合理的技术取舍。

## Q13：导弹模型是不是只用了一套统一的比例导引？

**A：**

不是。

当前项目中，AIM-120C 和 R-27ER 都不是简单“一条比例导引到底”，也不是完全同构。

两者都分为三个阶段：

- 助推段
- 中段制导段
- 末段制导段

但三个阶段的控制逻辑并不相同。

### 1. 助推段

助推段的核心任务不是精细逼近，而是：

- 快速建立速度；
- 调整初始姿态；
- 把导弹拉到合理拦截方向。

这一段更接近“姿态建立 + 能量建立”，不是单纯末段式比例导引。

### 2. 中段制导段

中段的核心任务是：

- 根据目标当前几何关系持续逼近；
- 结合预测拦截点修正导弹航迹；
- 为末段创造有利相对位置。

这一段可以理解为“预测拦截 + 导引修正”的复合过程。

### 3. 末段制导段

末段才最接近大家通常说的比例导引语义，也就是：

- 根据导弹-目标视线角变化；
- 持续调整法向控制；
- 把速度方向逐步逼向目标线。

因此，更准确的说法是：

**末段具有显著比例导引特征，但全程并不是只靠一条统一比例导引律。**

## Q14：AIM-120C 和 R-27ER 在项目实现中的关键差异是什么？

**A：**

关键差异不是“参数略有不同”，而是**制导责任结构不同**。

### AIM-120C

- 属于主动雷达制导导弹。
- 中后段更依赖导弹自身链路。
- 载机发射后有更大机动自由度。
- 更容易形成“发射后不必长时间持续照射”的攻击链。

### R-27ER

- 属于半主动雷达制导导弹。
- 更依赖载机或友机维持照射链。
- 如果照射链断裂，中制导和末段效能会明显受影响。
- 因此必须把稳定跟踪、照射保持和接力制导纳入同一条系统链。

所以，R-27ER 的难点不在于“导弹是不是能飞”，而在于“载机或友机能不能持续提供有效制导责任”。

## Q15：导弹在代码里是怎么实现的？

**A：**

当前项目中，导弹实现链的关键入口包括：

- `cap/adapters/missile_adapter.py`
- `simulation/r27er_missile.py`

需要重点掌握的对象和函数包括：

- `MissileSimulator`
- `R27ERMissileSimulator`
- `set_guidance_aircraft(...)`
- `apply_relay_guidance(...)`

其中：

- `MissileSimulator` 更偏通用导弹基类链。
- `R27ERMissileSimulator` 是对半主动弹特性的专门扩展。
- `set_guidance_aircraft(...)` 负责建立当前制导责任机。
- `apply_relay_guidance(...)` 负责在必要时把制导责任移交给新的友机。

## Q16：如果专家问“你们说三阶段，那具体怎么实现”，怎么回答？

**A：**

可以按下面这段回答：

“当前项目里，导弹发射后首先进入助推段，助推段主要完成姿态建立和能量建立，使导弹快速指向目标大致方向；随后进入中段制导段，中段会根据目标几何关系持续修正逼近轨迹，对于半主动弹还会同步检查照射链是否仍然有效；最后进入末段制导段，末段根据相对位置与视线角变化输出更强的逼近控制，并完成最终命中判定。也就是说，三阶段不是文档上的概念，而是代码里真实分段处理的。” 

## Q16.1：如果专家继续追问“助推段、中段、末段分别输入什么、处理中间量是什么、输出什么”，怎么回答？

**A：**

可以按照“输入-处理中间量-输出-边界条件”四层来答。

### 一、助推段

**输入：**

- 当前导弹位置、姿态、速度；
- 发射瞬间的目标相对方位；
- 当前载机或导引源提供的目标位置。

**处理中间量：**

- 导弹到目标的视线方向；
- 当前姿态和目标方向之间的偏差；
- 助推期剩余时间；
- 导弹当前可用推力和速度建立状态。

**输出：**

- 导弹在助推段的法向控制命令；
- 导弹姿态调整趋势；
- 推力工作下的速度快速建立。

**边界条件：**

- 助推段不是追求最终命中精度；
- 主要目标是把导弹“拉正、拉快、拉到可继续逼近的方向上”；
- 如果一发射就直接按末段逼近逻辑打，很容易在姿态和能量还没建立时造成轨迹浪费。

### 二、中段制导段

**输入：**

- 当前导弹状态；
- 当前目标状态；
- 当前导引源是否仍可提供有效制导支持；
- 当前导弹到目标距离。

**处理中间量：**

- 目标预测拦截点；
- 当前视线角和视线角变化率；
- 导弹与目标的相对几何关系；
- 半主动弹是否仍处于有效照射链内。

**输出：**

- 中段逼近控制命令；
- 是否继续维持当前制导责任；
- 是否有必要触发接力制导判断。

**边界条件：**

- 这一段不是简单直飞；
- AIM-120C 更偏“导弹自己持续逼近”；
- R-27ER 更偏“逼近过程仍依赖外部照射责任是否稳定”。

### 三、末段制导段

**输入：**

- 当前导弹和目标间的近距相对位置；
- 当前速度矢量；
- 当前视线角变化；
- 对于半主动弹，还包括照射是否还在有效保持。

**处理中间量：**

- 视线角速率；
- 法向机动需求；
- 终端几何是否还能维持稳定逼近；
- 若半主动链短时波动，是否仍在允许的盲持窗口内。

**输出：**

- 更强的末段逼近控制；
- 是否进入命中；
- 是否转入脱靶或终止状态。

**边界条件：**

- 末段更接近大家理解的比例导引语义；
- 但它仍然不是脱离整个责任链独立存在；
- 对 R-27ER 而言，末段前后照射链是否还能被维持，仍然是成败关键。

## Q16.2：如果专家要求你用更像伪代码的方式解释导弹三阶段，你怎么说？

**A：**

可以这样答：

## Q17：火控雷达为什么采用功能级建模，而不是更底层的电磁仿真？

**A：**

因为本项目上层真正需要的，不是每一拍回波细节，而是雷达在战术层能否完成三件事：

- 搜索
- 跟踪
- 锁定

只要能把这三种状态及其转移逻辑正确建出来，就已经足以支撑：

- 协同探测；
- 稳定跟踪门禁；
- 发射条件判断；
- 接力制导责任链。

因此，这里做的是“功能级而不是电磁级”，这是符合任务需求的合理建模层级。

## Q18：雷达功能级模型具体考虑了哪些因素？

**A：**

当前项目里，雷达模型综合考虑：

- 目标距离；
- 方位偏差；
- 俯仰角因素；
- 动态 RCS 修正；
- 多普勒盲区；
- 地杂波；
- 大气衰减；
- 天气修正；
- 下视条件差异。

这些因素共同决定当前目标到底处于：

- `SEARCH`
- `TRACK`
- `LOCK`

哪一种状态。

所以它不是“距离一到就锁定”的简化模型，而是一个综合评分后的功能状态机。

## Q18.1：如果专家继续追问“这些因素不是名词堆砌吗，到底怎么决定从搜索变成跟踪、从跟踪变成锁定”，怎么回答？

**A：**

这时不能只说“综合考虑很多因素”，而要把判断链讲清楚。

当前功能级雷达的核心思想不是做电磁回波反演，而是对“当前这架目标值不值得、能不能、稳不稳地进入更高一级火控状态”进行评分。可以把它理解成三步：

### 第一步：计算基础可探测性

先看目标在几何上是不是“基本可见”：

- 距离是否还在当前模式的可作用范围内；
- 方位角偏差是否还在天线主瓣允许范围内；
- 俯仰角是否超出下视或上视限制；
- 当前机头朝向和扫描扇区是否覆盖到了该目标。

如果这一步都过不了，目标连搜索候选都进不来。

### 第二步：计算质量折减

在“几何上可见”的基础上，再看质量会被哪些因素拉低：

- 目标动态 RCS 是否偏低；
- 是否处于多普勒盲区；
- 是否处于强地杂波背景；
- 是否存在下视惩罚；
- 是否存在天气和大气衰减；
- 是否受 ECM 干扰影响。

这一步的本质是：不是问“能不能看见”，而是问“看见得稳不稳、值不值得往更高状态推进”。

### 第三步：根据阈值决定状态推进

得到综合质量后，再决定：

- 质量只够粗发现，则保持在搜索；
- 质量足够稳定，则进入跟踪；
- 质量更高且连续维持，则进入锁定。

所以从搜索到跟踪、从跟踪到锁定，不是一个开关动作，而是“几何可行 + 质量足够 + 连续维持”三者共同作用的结果。

## Q18.2：如果专家要求你用更像伪代码的方式说明雷达功能级建模，你怎么回答？

**A：**

可以这样说：

```text
输入：本机状态 x_a，目标状态 x_t，当前雷达模式 mode，环境扰动 env

计算距离 d
计算方位偏差 az
计算俯仰偏差 el

如果 d 超出当前模式作用距离：
    返回 未发现

如果 az 或 el 超出扫描或火控允许范围：
    返回 未发现

计算基础可见分数 score_base
计算 RCS 修正 score_rcs
计算下视/地杂波惩罚 score_clutter
计算多普勒盲区惩罚 score_doppler
计算 ECM 惩罚 score_ecm
计算天气与衰减修正 score_env

总分 score = score_base + score_rcs - score_clutter - score_doppler - score_ecm - score_env

如果 score < 搜索阈值：
    状态 = 未发现
否则如果 score < 跟踪阈值：
    状态 = 搜索
否则如果 score < 锁定阈值：
    状态 = 跟踪
否则：
    状态 = 锁定

如果状态连续维持时间不足：
    不允许进入稳定火控结果
```

这段伪代码最重要的价值是把专家的疑问拆开了：它不是“有没有雷达”，而是“当前这架目标在当前姿态、距离、环境和干扰条件下，火控链能推进到哪一级”。

## Q19：RWR、ECM 这些在项目里真的有作用吗？

**A：**

有，而且它们的作用不是单独成页摆设，而是反向影响火控链。

项目里建立的是一个“探测-告警-干扰-质量退化”的闭环：

- 敌雷达探测到我机；
- 我机 RWR 感知威胁；
- 我机 ECM 或规避动作介入；
- 对方雷达跟踪质量和锁定稳定性发生变化；
- 这又进一步影响后续门禁、接力与模板切换。

因此，RWR 和 ECM 在项目里不是独立展示件，而是火控链扰动源。

## Q19.1：如果专家问“RWR 和 ECM 在当前代码里不是独立主角，那你们为什么还敢写进去”，怎么回答？

**A：**

因为它们在当前项目中的真实定位，本来就不是“单独主角算法”，而是**火控链质量调制因子**。

这里一定要避免夸大。更准确的说法是：

- RWR 的作用是把“对方雷达已经在看我”这件事转成我方可感知威胁；
- ECM 的作用是把“我方开始自保干预”这件事反向作用到对方火控质量；
- 这两者共同影响后续的稳定跟踪、门禁放行、模板切换和规避触发。

所以它们的价值不在于单独做一页炫技，而在于让“感知链、火控链、生存链”之间真正产生耦合。

## Q19.2：如果专家追问“那在答辩里该怎么讲，既不夸大，也不显得没做”，怎么回答？

**A：**

最稳的讲法是：

“本项目没有把 RWR 和 ECM 当成单独割裂的展示模块，而是把它们纳入火控闭环。也就是说，敌方雷达对我方的探测不只是让目标被发现，还会引出我方告警、自保和干扰动作，而这些动作又会反向影响对方锁定质量与后续武器链稳定性。这样做的意义，是让仿真中的火控关系更接近真实对抗中的双向博弈，而不是单向探测。” 

## Q20：高层战术语义是怎么变成底层实际控制输出的？

**A：**

这是项目里非常关键的一条执行链。

当前链路可以概括成：

`战术模板/机动原语 -> 离散三元组 -> 低层策略网络 -> 四维连续控制量 -> JSBSim`

具体过程是：

1. 上层模板或机动原语先给出高层意图。
2. 这个意图被离散化为三元组：
   - 高度命令
   - 航向命令
   - 速度命令
3. `_build_lowlevel_input_for_agent(...)` 把三元组和当前飞行状态拼成网络输入。
4. `BaselineActor` 做前向推理。
5. `_raw_bins_to_norm_act(...)` 把离散输出档位映射成连续控制值。
6. 最终得到副翼、升降舵、方向舵和油门四维控制量。
7. 这些量进入 JSBSim，驱动物理状态更新。

这条链说明，项目并不是把模板直接硬写成飞行轨迹，而是真正经过了一个低层控制翻译器。

## Q20.1：如果专家追问“12 维输入具体是哪 12 维”，怎么回答？

**A：**

当前低层链里，输入给 `BaselineActor` 的不是一句抽象命令，而是一个 12 维浮点向量。

这 12 维可以分成两部分：

### 前 3 维：高层语义命令

- 高度命令语义；
- 航向命令语义；
- 速度命令语义。

这三维不是最终物理量，而是已经经过归一化和合法范围裁剪后的高层控制意图。

### 后 9 维：当前飞机关键状态

当前项目里，这 9 维和低层控制约定是一致的，主要包含：

- 当前高度；
- 滚转角的正弦或余弦表示；
- 俯仰角的正弦或余弦表示；
- 前向速度分量；
- 侧向速度分量；
- 垂向速度分量；
- 校准空速或等效速度信息。

这样拼接后的 12 维输入，含义就变成了：

**“我现在想这么飞，并且飞机当前正处于这种状态。”**

低层网络的任务，不是凭空想动作，而是根据这两类信息共同推断此刻最合适的控制档位。

## Q20.2：`BaselineActor` 在这条链里究竟做了什么？

**A：**

`BaselineActor` 的职责非常明确：

- 它不是高层战术决策器；
- 它也不是物理积分器；
- 它是“高层语义到低层控制”的执行翻译器。

更具体一点说，它完成四件事：

1. 读取 12 维输入；
2. 结合内部时序记忆状态，判断当前动作应该有多强；
3. 分别给四个控制通道输出离散动作档位；
4. 把结果交给后处理映射到真实控制量。

也就是说，它的核心价值是：

**同一个高层语义，在不同飞行状态下会被翻译成不同力度的控制输出。**

这正是它相比静态查表控制的价值所在。

## Q20.3：如果专家继续追问“`BaselineActor` 的输出不是直接连续量，那中间经历了什么”，怎么回答？

**A：**

中间经历了一个“离散档位 -> 连续控制量”的映射过程。

流程是：

1. `BaselineActor` 输出 4 个离散动作头的档位编号；
2. 这些档位组合就是当前这一拍的 `act`；
3. `_raw_bins_to_norm_act(...)` 把档位编号映射到规范化连续区间；
4. 对前三个通道一般映射到类似 `[-1, 1]` 范围；
5. 对最后一个油门通道映射到油门开度区间；
6. 最终形成：
   - 副翼控制量；
   - 升降舵控制量；
   - 方向舵控制量；
   - 油门控制量。

因此，`act` 并不是最终控制量本身，而是网络挑出来的离散动作档位组合。

## Q20.4：为什么要先输出离散档位，而不是让网络直接输出连续舵面？

**A：**

这样做的原因主要有三点：

- 第一，训练更稳定。直接连续输出容易导致控制抖动或不稳定探索。
- 第二，离散档位更便于和高层语义耦合，因为高层本身也是离散语义。
- 第三，便于约束安全边界，比如限制某些极端动作组合不被直接输出。

所以，这不是一种“简化偷懒”，而是一种兼顾可训练性、可解释性和执行稳定性的设计。

## Q21：什么是离散三元组？

**A：**

离散三元组是高层机动意图的统一表达方式：

- `altitude_cmd_id`
- `heading_cmd_id`
- `velocity_cmd_id`

它的意义不是直接控制舵面，而是把高层动作语义标准化。

比如：

- “小角度左转”
- “快速压缩距离”
- “轻微抬升保持能量”

这些都不直接变成舵面，而是先映射成对应的高度、航向、速度档位编号，然后再进入低层网络。

这样做的好处是：

- 高层战术表达统一；
- 低层网络输入稳定；
- 不同模板可以复用同一套动作接口。

## Q21.1：如果专家追问“那这些三元组到底长什么样，怎么和具体机动原语对应”，怎么回答？

**A：**

这里要把“语义层”和“执行层”分开讲。

三元组不是直接写“左转 30 度、爬升 500 米”这种自然语言，而是写成：

- 高度通道取哪一档；
- 航向通道取哪一档；
- 速度通道取哪一档。

例如：

- 保持平飞直飞：
  - 高度档取“保持”
  - 航向档取“保持”
  - 速度档取“保持巡航”
- 左转压缩：
  - 高度档取“轻微保持或小幅爬升”
  - 航向档取“左转若干档”
  - 速度档取“加速压缩”
- 规避脱离：
  - 高度档取“保持或小幅下降”
  - 航向档取“大角度偏转”
  - 速度档取“加速脱离”

所以专家真正要理解的是：

**三元组不是飞机动作本身，而是飞机动作的上层离散语义编码。**

## Q21.2：如果专家问“转弯这种动作，在你们系统里到底是怎么被表示和执行的”，怎么回答？

**A：**

转弯不是一个单独魔法函数，而是“航向档位主导，高度档和速度档配合”的结果。

以左转为例，执行链可以拆成四步：

1. 上层机动原语先决定这是“小角度修正”还是“大角度战术偏转”；
2. 航向通道选定对应的左转档位；
3. 高度通道决定转弯时是否需要保高度、轻微爬升或轻微下降；
4. 速度通道决定转弯是保持能量、压缩距离还是脱离加速。

然后这组三元组进入低层网络，低层网络再结合当前滚转、俯仰、速度和高度状态，把“左转档位”翻译成真实副翼、升降舵和方向舵控制量。

所以转弯在项目里不是一句“turn left”，而是：

**高层语义选航向档，低层控制把航向档翻译成稳定可执行的滚转-俯仰-油门联动。**

## Q22：`bins` 到底是什么意思？

**A：**

`bins` 可以直接理解成“离散档位编号”。

网络输出时，不是直接输出连续的舵面值，而是先输出每个控制通道应该选哪个档位。这个档位编号就是 `bins`。

例如某一拍输出 `[20, 18, 22, 15]`，含义不是副翼等于 20，而是：

- 第一个控制通道选第 20 档；
- 第二个控制通道选第 18 档；
- 第三个控制通道选第 22 档；
- 第四个控制通道选第 15 档。

然后 `_raw_bins_to_norm_act(...)` 再把这些档位编号映射成实际连续控制值。

因此，`bins` 是“离散动作空间中的档位语义”，不是最终控制量本身。

## Q23：`BaselineActor` 和 `baseline_model.pt`、`actor_990.pt` 到底是什么关系？

**A：**

这里一定要区分训练阶段和在线执行阶段。

### 训练阶段

- 采用 PPO 等强化学习框架训练低层控制策略；
- 训练时会同时存在策略网络和价值网络；
- 训练出来的某些 checkpoint 例如 `actor_990.pt`，本质上是训练态策略权重。

### 在线执行阶段

- 在线不再训练，只做推理；
- 使用的是统一的执行网络结构，例如 `BaselineActor`；
- `baseline_model.pt` 是适配该执行结构后的在线权重文件。

因此，可以说：

**`actor_990.pt` 更偏训练产物，`baseline_model.pt` 更偏在线部署产物，而 `BaselineActor` 是在线执行模块。**

## Q24：为什么要用低层强化学习策略，而不是手写 PID 或规则控制？

**A：**

原因主要有三点：

- 第一，高层动作种类多，姿态切换复杂，手写规则很容易在跨动作切换时不平滑。
- 第二，战术动作不仅要“能做出来”，还要在不同飞行状态下做得稳定，学习型策略更擅长处理这种状态依赖。
- 第三，项目重点是打通高层语义到底层执行的闭环，低层强化学习策略正好承担这种“语义翻译器”的角色。

当然，这并不意味着 PID 没价值，而是当前项目场景里，强化学习低层控制更适合承接多样化机动原语。

## Q24.1：如果专家问“敌方到底怎么做决策，不会也是手工脚本吧”，怎么回答？

**A：**

当前正式样本里的敌方不是单一脚本，而是“场景约束 + 敌方 AI 适配器 + 动作执行链”的组合。

真实入口包括：

- `cap/adapters/enemy_ai_adapter.py`
- `cap/cap_task_action_helpers.py`
- `cap/tests/ch6_validation_scenarios.py`
- `cap/tests/scenario_generator.py`

在正式三场里，敌方主要有两种工作方式：

### 第一种：自由博弈 `freeplay`

场景一和场景二属于这一类。  
含义是：

- 只固定初始几何和场景约束；
- 开局后不持续手工给敌方航向脚本；
- 后续交给敌方适配器和原生敌方 AI 路线自己演化。

### 第二种：短开局控制 + 自由博弈 `hybrid_opening`

场景三属于这一类。  
含义是：

- 只在极短的开局窗口里，为了塑造低空突防样本，给敌方一个加速爬升开局；
- 之后释放回原生敌方 AI；
- 后段仍然不是人为拖着敌方飞。

因此，正式三场不是“拿敌方当木偶”，而是在明确场景契约下，让敌方形成真实、可复现、可解释的压力。

## Q24.2：如果专家追问“敌方战术逻辑到底是什么”，怎么回答？

**A：**

当前敌方适配器的设计目标在代码开头写得很清楚，核心是：

- 严格把敌机限制在任务允许边界内；
- 用编队波次而不是无脑持续压入；
- 尽量保持双机编组；
- 呈现“南向逼近 -> 北向拉开 -> 北向重整 -> 南向再攻击”的节奏。

从 `EnemyAIAdapter` 的内部结构看，敌方至少维护了：

- 编组上下文；
- 波次状态；
- 当前阶段；
- 重组位置；
- 再攻击距离；
- 硬脱离窗口；
- 压力等级和局部优劣判断。

所以敌方完全可以被描述成：

**一个受任务边界约束、具有波次化逼近-脱离-重组节奏、并能根据局部压力调节行为的对抗方。**

## Q24.3：如果专家问“敌方机动逻辑具体是怎么落到动作上的”，怎么回答？

**A：**

敌方和我方一样，不是直接输出舵面，而是先输出高层动作，再落到底层执行。

从 `cap_task_action_helpers.py` 可以看到：

- 每一拍敌方也会走 `_get_enemy_action(...)`
- 再调用 `enemy_adapter.get_enemy_action(...)`
- 最终返回的也是三元组式离散动作接口

也就是说，敌方同样经历：

- 战术层选择；
- 动作语义编码；
- 低层控制执行。

这点在答辩里非常重要，因为它说明你的对抗不是“我方走真实执行链，敌方走真值脚本瞬移链”，而是双方都要经过可执行动作接口，只是我方更强调任务级协同与模板组织。

## Q25：机动原语为什么是这个项目的重要组成部分？

**A：**

因为战术模板不是一句话，而是由一串具体动作组织起来的。如果没有统一的基础机动原语和复合机动原语，模板就只能停留在概念层面。

项目里的机动原语分两类：

- 基础机动原语：
  - 平飞
  - 转弯
  - 爬升
  - 俯冲
  - 加速
  - 减速
- 复合机动原语：
  - Crank
  - Tactical Crank
  - Short Skate
  - Beam
  - Notch Back
  - Rear Formation 等

这些原语是模板执行的最小动作单元。

## Q25.1：如果专家单独问“那敌方在三次正式仿真里各自是什么控制方式”，怎么回答？

**A：**

这个问题可以直接按正式三场说：

### 场景一

- 敌方控制模式：`freeplay`
- 含义：只固定初始低风险正面对进几何，开局后不再持续脚本牵引敌方转向

### 场景二

- 敌方控制模式：`freeplay`
- 含义：只固定中风险持续压制的初始几何与受扰条件，后续敌方仍走原生对抗演化

### 场景三

- 敌方控制模式：`hybrid_opening`
- 含义：只在低空突防开局的极短窗口内给敌方一个加速爬升开局，随后释放回原生敌方 AI

所以正式三场的敌方不是“全程手工脚本”，而是：

**场景层塑形，后段主要自由博弈。**

## Q25.2：如果专家继续问“那你们为什么认为这样的敌方设计是可信的”，怎么回答？

**A：**

因为它同时满足三件事：

- 第一，可复现。初始几何和控制契约是固定的；
- 第二，有对抗性。后段不是静态脚本，而是会对我方行为产生响应；
- 第三，可解释。你能说清楚每个场景敌方被固定了什么、被释放了什么。

这比“全程手工演一段”更可信，也比“完全随机不受控”更适合正式答辩验证。

## Q26：如果专家问“转弯具体怎么定义和控制”，怎么回答？

**A：**

可以这样回答：

“当前项目里，转弯不是直接写成一条几何圆弧，而是先由高层给出航向增量语义，再映射成离散航向档位，随后低层控制网络结合当前滚转、俯仰、速度和空速状态，把这个航向语义转成副翼、升降舵、方向舵和油门控制量，最后由 JSBSim 积分得到真实转弯轨迹。因此，转弯动作既有明确的高层意图表示，也有真实物理承接。” 

## Q27：机动原语有没有做过执行精度验证？

**A：**

做过。

项目对基础机动和复合机动都进行了误差验证，验证结论是：

- 平飞、转弯、拉起、俯冲、加速、减速等基础动作可稳定执行；
- Crank、Tactical Crank、Short Skate 等复合动作也能在可接受误差范围内完成；
- 因此，机动执行层具备把战术动作真实落到飞行动力学上的能力。

这一点非常关键，因为它回答了一个常见质疑：战术模板是不是只是“纸上战术”。当前验证表明不是。

# 四、协同探测、协同跟踪与接力制导

## Q28：协同探测到底要解决什么问题？

**A：**

协同探测要解决的是：

**预警机提供的是粗、噪、可能短时丢失的目标信息，系统如何在有限时间内组织多机协同，把这类粗信息变成稳定、连续、足够精确的火控前态势。**

所以协同探测的输入和输出边界很清楚：

- 输入起点：AWACS 粗探测信息；
- 输出终点：为火控链提供稳定感知与接手基础。

它不是最终火控链本身，但它决定火控链能不能顺利建立。

## Q29：为什么要设计七层协同探测架构？

**A：**

因为从“粗信息”到“可执行接手几何”并不是一步能完成的，中间至少要经过信息、估计、预测、区域构造、规划、协调和执行七个层次。

这七层分别解决不同问题：

- 信息层：拿到原始 AWACS 粗信息；
- 估计层：对当前目标状态做较稳定估计；
- 预测层：考虑目标机动趋势；
- 区域层：把不确定性转成目标区域；
- 规划层：给多机生成引导点和扫描组织；
- 协调层：协调速度、扇区与时序；
- 执行层：把规划真正转成飞机动作与雷达模式。

如果不分层，系统很容易把“目标在哪里”“该怎么分配扇区”“该谁先到”“当前该扫还是定向跟踪”混在一起，最终既难解释，也难维护。

## Q29.1：七层协同探测每一层分别在做什么，能不能讲得更细？

**A：**

可以逐层展开。

### 第一层：信息层

目标是：

- 接入 AWACS 粗信息；
- 过滤非法、过期或明显不可信的目标条目；
- 形成当前可用于决策的初始观测集合。

这一层回答的是：

**“现在系统手里到底拿到了什么原始敌情信息。”**

### 第二层：估计层

目标是：

- 对当前敌方位置、速度、航向趋势做更稳定估计；
- 抑制测量噪声和瞬时跳变；
- 为后续预测提供更平滑输入。

这一层回答的是：

**“把粗测量变成更像真实状态的估计值。”**

### 第三层：预测层

目标是：

- 结合当前估计状态；
- 预测敌方短时未来位置；
- 估计目标可能的机动扩散趋势。

这一层回答的是：

**“敌机如果继续这么飞，未来大概会出现在什么区域。”**

### 第四层：区域层

目标是：

- 把点估计扩展成区域估计；
- 根据敌方分散程度、不确定性和机动趋势形成目标区域；
- 给后续扫描和接手提供空间范围。

这一层回答的是：

**“我不该只盯一个点，而应该围绕多大一块区域来组织搜索。”**

### 第五层：规划层

目标是：

- 根据目标区域为多机生成引导目标点；
- 决定左右两组双机该往目标区域的哪个侧面接近；
- 确定编队级接手几何。

这一层回答的是：

**“谁从哪边接近、谁去占哪一个几何位置。”**

### 第六层：协调层

目标是：

- 协调长僚机到达时序；
- 决定该减速还是加速；
- 决定扫描模式；
- 决定扇区如何分配以避免重复搜索。

这一层回答的是：

**“大家怎么配合才能既不撞车、又不重复扫、还能尽量同步到位。”**

### 第七层：执行层

目标是：

- 把前面规划和协调结果变成航向、速度、扫描模式、扇区和动作命令；
- 真正驱动飞机与雷达去工作。

这一层回答的是：

**“前面算出来的方案，现在如何真正落地执行。”**

## Q29.2：如果专家问“为什么非要分这七层，能不能合并”，怎么回答？

**A：**

可以合并，但代价很大。

如果把七层粗暴合并，会立刻出现三个问题：

- 第一，原始误差信息和后续几何规划混在一起，导致问题难定位；
- 第二，速度协调、扇区分配和扫描模式切换会变成黑盒，很难解释；
- 第三，验证时无法回答“到底是哪一环起作用”。

而七层结构最大的价值，就是把：

- 信息可信度；
- 不确定性传播；
- 搜索区域构造；
- 编队接近几何；
- 资源协调；
- 执行落地

这几件不同性质的工作拆开。这样系统才可解释、可调试、可复盘。

## Q30.1：协同探测在代码里最关键的真实入口有哪些？

**A：**

如果要从代码角度回答，至少要掌握这些入口：

- `filter_valid_awacs_info(...)`
- `estimate_enemy_center(...)`
- `predict_enemy_motion(...)`
- `build_confidence_region(...)`
- `plan_guidance_points(...)`

它们分别对应：

- 有效信息筛选；
- 敌方中心估计；
- 目标运动预测；
- 区域构造；
- 编队引导点规划。

再往下才会进入速度协调、扫描模式切换和扇区分配。

## Q30.2：如果专家问“协同探测真正输出的是什么”，怎么回答？

**A：**

协同探测真正输出的，不是某个漂亮的中间变量，而是三类可执行结果：

- 第一类：更稳定的敌方中心和目标区域；
- 第二类：多机的接手引导几何；
- 第三类：扫描模式、扇区和时序组织建议。

换句话说，它最终输出的是：

**“我方多机现在该朝哪里去、用什么方式扫、怎样配合去把目标真正接手住。”**

## Q31.1：协同探测为什么能说自己是“不确定性传播-协同闭环”方法？

**A：**

因为它确实同时做了两件事。

### 第一件事：不确定性传播

系统没有把 AWACS 粗信息当成真值，而是承认：

- 位置有误差；
- 航向可能变化；
- 目标可能分散；
- 预警链可能短时失配。

于是它把“粗点信息”扩展成了“目标区域”，并让区域半径随不确定性变化。

### 第二件事：协同闭环

系统不是算完区域就结束，而是继续用这个区域去驱动：

- 引导；
- 速度协调；
- 模式切换；
- 扇区分配；
- 机载雷达接手；
- 后续稳定跟踪。

这就形成了从“不确定信息”到“协同行动”再到“新的稳定信息”的闭环。

## Q33.1：如果专家质疑“综合仿真里的探测指标低，是不是算法退化了”，怎么回答？

**A：**

不能直接顺着这个质疑去承认“退化”，要把口径讲清楚。

正确回答是：

“专项协同探测验证重点考察的是探测链本体，因此场景更受控、窗口更聚焦；综合正式仿真则把发射、规避、接力和再组织一并纳入，探测资源必须同时服务交战链和生存链，所以后者的全程覆盖率不宜与专项验证直接等价比较。前者主要证明算法本体能力，后者主要证明算法在完整作战链中的可用性。” 

## Q30：七层协同探测架构在当前代码里有没有真实落点？

**A：**

有。

当前实现不是纯理论七层图，而是有真实代码链路支撑。典型函数和入口包括：

- `filter_valid_awacs_info(...)`
- `estimate_enemy_center(...)`
- `predict_enemy_motion(...)`
- `build_confidence_region(...)`
- `plan_guidance_points(...)`

再往下还会进入：

- 扫描模式选择；
- 扇区划分；
- 速度协调；
- 编队引导；
- 低层动作执行。

因此，这七层不是“PPT 语言”，而是对当前实际链路的分层抽象。

## Q31：协同探测里的优化目标是什么？

**A：**

原理上，协同探测以最小化加权代价函数为目标，决策变量主要是各机航向和速度。

代价函数主要考虑：

- 最大到达时间；
- 编队协调代价；
- 燃油或动作成本；
- 目标丢失风险。

但要注意，当前实现并没有把它做成一个每拍求解的统一连续优化器，而是采用了：

- 分层近似求解；
- 离散候选搜索；
- 几何解析计算；
- 规则驱动的模式切换。

所以在答辩中要避免说成“我们在线精确求解了一个全局优化问题”，更准确的表达是：

**我们保留了优化目标的思想，但实现上采用了更适合在线实时运行的分层近似求解框架。**

## Q32：4.3 和 4.4 到底是什么关系？

**A：**

这是一个容易被问到的问题。

### 4.2 的作用

4.2 讲的是“协同探测为什么要分七层”，也就是结构性拆分。

### 4.3 的作用

4.3 讲的是“七层结果如何被串成一个可执行的核心逻辑主链”。它重点在：

- 目标状态估计；
- 不确定性传播；
- 目标区域构造；
- 编队引导目标生成。

也就是说，4.3 更像“主干算法链”。

### 4.4 的作用

4.4 讲的是“为了让 4.3 真的落地，还要如何组织速度协调、扫描模式和扇区分配”。它更像“资源协调与执行细化层”。

因此，三者关系不是重复，而是：

- 4.2 讲分层框架；
- 4.3 讲主干链；
- 4.4 讲执行资源协调。

## Q33：协同探测专项验证为什么那么高，综合实战仿真里有些覆盖率反而低？

**A：**

这个问题必须严谨回答，不能乱说。

当前分析结论是：

- 专项验证和综合仿真的指标定义大体一致；
- 但二者任务边界和统计窗口不同，因此数值不能简单横向等价比较。

专项验证更像“探测能力压测题”，特点是：

- 场景更受控；
- 目标更聚焦；
- 主要考察首探、补齐、模式切换和恢复能力。

综合正式仿真更像“完整交战闭环题”，特点是：

- 目标更快进入交战链；
- 后段还要让位给发射、规避、接力和再组织；
- 雷达资源不会只服务满覆盖，还要服务火控链和生存链。

因此，在正式综合仿真中，覆盖率回落并不等于协同探测无效，而是说明探测资源在更复杂任务中要和火控、生存、门禁一起分配。

## Q33.2：如果专家问“协同探测指标具体是怎么算的”，怎么回答？

**A：**

这部分必须按代码口径回答，不能泛泛讲。

当前综合验证里，协同探测的基本统计对象是：

**每一拍我方联队总共在火控层面看住了多少架敌机。**

在 Chapter 6 的时间线上，这个量体现为：

- `radar_track_count`

它的含义不是单机看到几架，而是：

- 先收集四架我机当前火控雷达在轨目标 ID；
- 做并集；
- 再数并集里有几架敌机。

在此基础上，再算三类核心指标。

### 第一，平均探测覆盖率

公式含义是：

`联队在轨目标数的平均值 / 敌方目标总数`

例如敌方共 4 架，而你平均每拍能看住 2 架，那么平均探测覆盖率就是 `2/4 = 50%`。

### 第二，全覆盖连续性

公式含义是：

`满足“联队在轨目标数 = 敌方总数”的拍数 / 统计窗口总拍数`

它回答的问题是：

**你不是偶尔全探一下，而是有多少时间真正维持了全目标同时在轨。**

### 第三，任意目标连续性

公式含义是：

`满足“联队在轨目标数 > 0”的拍数 / 统计窗口总拍数`

它回答的问题是：

**系统有没有长时间彻底黑屏。**

所以：

- 平均探测覆盖率看整体覆盖水平；
- 全覆盖连续性看满额覆盖维持能力；
- 任意目标连续性看链路有没有断。

## Q33.3：如果专家继续追问“正式汇报到底该用哪个统计窗口讲协同探测”，怎么回答？

**A：**

当前最稳的说法是：

- 如果你在讲协同探测方法本体，就优先使用前段窗口；
- 如果你在讲整场综合作战资源分配，才用全程窗口。

更具体地说：

- 专项协同探测验证更适合聚焦“雷达激活后”的窗口；
- 第六部分正式三场里，若讨论协同探测本体，应聚焦“激活 -> 补齐 -> 稳定交战就绪”这一段；
- 如果把后面的发射、规避、接力和再组织都混进来，探测指标会被自然稀释。

所以答辩时一定要说明：**不同窗口回答的是不同问题。**

## Q34：场景二为什么特别能证明协同探测方法有效？

**A：**

因为场景二存在预警链首轮失配，而系统仍然在较短时间内完成了：

- 预警信息恢复；
- 机载火控接手；
- 目标补齐；
- 稳定交战就绪建立。

它证明的不是“环境完美时能探到”，而是：

**即使外层预警链出现失配，系统仍能依靠协同探测与机载雷达接手把主链拉回来。**

这比场景一的常规完整性验证更能证明鲁棒性。

## Q35：协同跟踪和协同探测的区别是什么？

**A：**

协同探测解决的是“看见并接手”的问题，协同跟踪解决的是“在发射前形成足够稳定的火控前提”的问题。

可以这样理解：

- 协同探测的终点，是把粗态势变成可用态势；
- 协同跟踪的终点，是把可用态势变成满足发射门禁的稳定态势。

所以协同跟踪并不是探测的重复，而是火控前门禁的前置条件。

## Q35.1：如果专家追问“那协同跟踪到底在什么时候开始，什么时候结束”，怎么回答？

**A：**

按当前项目口径，协同跟踪不是从仿真一开始就单独存在，而是在协同探测把目标接入可用态势之后，继续向“火控可发射”推进的那一段。

最容易讲清楚的说法是：

- 协同探测重点对应“进入 200km 激活后到目标补齐、建立可用态势”；
- 协同跟踪重点对应“从补齐之后到首次稳定交战就绪建立”；
- 再往后才进入“发射门禁是否放行”和“接力是否需要介入”。

如果用你项目里更熟悉的阶段语言来讲，可以说：

- 协同探测更偏向 `200km 激活 -> 看见 -> 补齐 -> MELD`
- 协同跟踪更偏向 `MELD -> MTR -> LR` 这一段

也就是说，协同跟踪本质上是探测链和武器链之间的桥。

## Q36：稳定跟踪门禁在代码里怎么实现？

**A：**

关键入口位于：

- `cap/cap_guidance_helpers.py`

重点函数包括：

- `_update_stable_tracking_window(...)`

当前逻辑核心包括：

- 跟踪质量阈值；
- 至少双机有效跟踪；
- 持续时间窗口；
- 抗抖动宽限时间；
- 最终形成 `stable_ready` 状态。

也就是说，系统不是“一看到目标就认为能发射”，而是要满足一个显式可累计的稳定跟踪条件。

## Q36.1：如果专家追问“`stable_ready` 到底是不是一个瞬时标志，还是一个累计结果”，怎么回答？

**A：**

它本质上是一个累计结果，不是瞬时一拍的真假值。

这点要讲清楚，因为很多人容易误以为“某一拍锁住了就算 ready”。当前项目不是这样。

更准确地说，`stable_ready` 的形成要同时满足：

- 当前目标质量达到跟踪要求；
- 有足够数量的友机形成有效跟踪；
- 这种状态持续了一段时间；
- 中间即便有短时抖动，也要看是否落在宽限窗口内；
- 只有累计结果过线，才记为稳定交战就绪。

所以 `stable_ready` 的含义不是“这一拍看上去不错”，而是“前一段时间内已经形成足够稳定的双机火控前提”。

## Q36.2：如果专家要求你把稳定跟踪门禁说成更接近算法流程，怎么回答？

**A：**

可以用这段：

```text
输入：当前目标跟踪质量 q，当前有效跟踪友机数 n，历史稳定时间窗口 W

如果 q 低于质量阈值：
    清空或回退稳定累计

如果 n 小于最小协同跟踪要求：
    清空或回退稳定累计

如果 q 达标 且 n 达标：
    累加稳定时间

如果中间短时跌落但仍在宽限窗口内：
    不立刻清零，只做部分保留

如果累计稳定时间 >= ready 阈值：
    stable_ready = True
否则：
    stable_ready = False
```

这能让专家立刻看出：你的门禁不是拍脑袋，而是“质量、数量、时间、抗抖动”四个条件共同决定。

## Q37：接力制导为什么是这个项目的重要部分？

**A：**

因为我方主导弹体系中存在半主动弹，导弹能否持续有效制导并不只取决于导弹本体，还取决于制导责任是否能够维持。

因此，接力制导不是锦上添花，而是半主动弹体系下攻击链能否延续的重要保障。

它解决的问题是：

- 原制导机被击毁怎么办；
- 原制导机被迫规避怎么办；
- 原制导机距离拉开或生存压力过大怎么办；
- 当前另一个友机是否能更好接替制导责任。

## Q38：接力制导在代码里怎么体现？

**A：**

关键实现包括：

- `apply_relay_guidance(...)`
- `_update_relay_guidance(...)`

当前逻辑不是简单“随便换一架机”，而是：

1. 先判断当前导弹是否需要接力；
2. 识别触发原因，例如原制导机生存性下降、跟踪质量下降、规避或距离问题；
3. 从其他可用友机中找候选机；
4. 比较候选机的当前跟踪质量是否明显更适合承担责任；
5. 满足条件才执行制导责任转移。

所以接力制导本质上是“责任链切换”，而不是“目标链切换”。

## Q38.1：如果专家继续追问“接力制导到底什么时候触发，判断步骤是什么”，怎么回答？

**A：**

接力制导不是导弹一发出去就固定启用，而是满足“原责任机继续维持责任变得不合适”时才触发。

实际可以拆成五问：

1. 这枚导弹当前是否仍处于需要外部责任维持的阶段；
2. 当前责任机是否还活着、还能看住、还能照住、还能承担；
3. 当前责任机是不是已经进入强规避、生存压力过大或几何位置明显恶化；
4. 其他友机中有没有更合适的候选者；
5. 候选者接手后，是否真的比原责任机更稳。

只有这五问一路往下走通了，接力才会执行。

所以接力不是“谁离得近谁接”，而是“谁最有希望把责任链继续维持下去谁接”。

## Q38.2：如果专家问“对 AIM-120C 和 R-27ER，接力意义是不是一样”，怎么回答？

**A：**

不一样。

对主动弹来说，接力更多是中段责任优化问题；  
对半主动弹来说，接力更接近“这条武器链还能不能继续成立”的关键问题。

因此在当前项目里，接力制导的必要性对半主动体系更强。也正因为这样，接力不是附属功能，而是让半主动弹体系具备现实作战可用性的关键补偿机制。

## Q38.3：如果专家追问“发射门通过率和接力制导成功率具体怎么计算”，怎么回答？

**A：**

这两个指标都必须区分 `raw` 和 `unique` 两套口径。

### 发射门通过率

当前代码会同时统计：

- 原始通过次数 `prelaunch_gate_pass_count`
- 原始阻断次数 `prelaunch_gate_block_count`
- 去重通过次数 `prelaunch_gate_unique_pass_count`
- 去重阻断次数 `prelaunch_gate_unique_block_count`

因此有两种通过率：

#### 原始通过率 `raw`

公式是：

`pass_count / (pass_count + block_count)`

它反映的是：

**所有门禁请求事件里，有多少次被放行。**

#### 去重通过率 `unique`

公式是：

`unique_pass_count / (unique_pass_count + unique_block_count)`

这里去重不是简单只看第一次，而是按射手-目标组合并结合时间窗聚合，避免同一机会在短时被重复请求把统计刷高。

因此：

- `raw` 更像内部诊断门禁请求强度；
- `unique` 更适合放在 PPT 和结论里做正式表达。

### 接力制导成功率

接力也一样分两套：

- 原始尝试数 `relay_attempt_count`
- 原始成功数 `relay_success_count`
- 去重尝试数 `relay_unique_attempt_count`
- 去重成功数 `relay_unique_success_count`

于是：

- 原始成功率 = `relay_success_count / relay_attempt_count`
- 去重成功率 = `relay_unique_success_count / relay_unique_attempt_count`

正式答辩时最稳的原则是：

**对外优先讲 unique，raw 主要用于解释系统是否在某段时间里频繁尝试。**

## Q38.4：如果专家继续问“为什么不能全部用 raw”，怎么回答？

**A：**

因为 `raw` 容易被短时间重复请求放大。

例如：

- 同一架射手在同一目标上短时间内反复请求门禁；
- 同一条责任链在短时间内多次重评接力机会。

如果全用 `raw`，就会把“系统很勤奋地反复判断”误看成“系统形成了很多独立有效机会”。

而 `unique` 更接近你在答辩里真正想表达的内容：

- 独立有效发射机会有多少；
- 独立有效接力机会有多少。

## Q39：协同探测、协同跟踪、接力制导三者在作战链上的关系是什么？

**A：**

三者是逐层递进关系：

- 协同探测：解决“看见和接手”；
- 协同跟踪：解决“发射前是否足够稳”；
- 接力制导：解决“发射后责任链是否能维持”。

也就是说，它们分别对应：

- 发射前的感知建立；
- 发射前的火控稳定；
- 发射后的责任延续。

这三段合起来，才是完整的火力组织链。

# 五、战术模板与分层决策

## Q40：为什么要做战术规则模板，而不是直接端到端学？

**A：**

因为当前任务是高约束、高解释性要求的 CAP 防御任务，专家最关心的不只是“结果好不好”，还包括：

- 为什么这么打；
- 什么时候切；
- 为什么换模板；
- 为什么进入规避；
- 为什么门禁没开。

战术规则模板天然适合表达这些内容，因为它具备：

- 状态机结构；
- 清晰的进入和退出条件；
- 可解释的动作序列；
- 便于复盘的战术语义。

因此，战术规则模板是把“空战经验”转成“机器可调用规则单元”的关键中间层。

## Q41：项目里有哪些核心战术模板？

**A：**

当前核心模板包括七类：

- 拖曳射击
- 钳形夹击
- 上下夹击
- 前后攻击
- 并排射击
- 战术规避
- 战术回转

其中：

- 前五类偏攻击组织；
- 后两类偏生存与重组。

## Q42：这些模板不是概念图吗，怎么落到代码里？

**A：**

当前实现里，模板不是单张示意图，而是有真实代码链路：

- 模板选择入口：
  - `cap/cap_tactic_helpers.py`
  - `cap/tactic_selector.py`
- 模板执行落点：
  - `TacticExecutorAdapter`
  - `formation_guidance.py`
  - 机动原语层

模板在代码里体现为：

- 当前所处阶段；
- 当前可选模板集合；
- 当前模板保持时长；
- 是否满足切换条件；
- 模板下对应的动作序列和参数风格。

所以模板不是“画在 PPT 上的概念”，而是在线参与决策的结构化对象。

## Q43：你们当前模板选择到底是怎么做的？

**A：**

当前正式主链里，模板选择的前端主驱动不是意图识别，而是：

- 风险区；
- 控制距离节点；
- 当前态势图；
- 敌我几何关系；
- 角色分工与模板保持逻辑。

可以概括成：

`风险区/节点/几何/当前模板状态 -> 候选模板 -> 适配筛选 -> 保持或切换`

这是当前代码实际运行口径，也是答辩中最应该坚持的真实说法。

## Q43.1：如果专家追问“当前模板选择的真实调用顺序是什么”，怎么回答？

**A：**

可以按真实调用逻辑回答：

1. 先由 `picture` 层形成当前可决策态势；
2. 再由风险区和控制距离节点约束当前候选范围；
3. `TacticSelector.select_tactic(...)` 在当前几何、阶段和上下文下筛选可用模板；
4. `TacticExecutorAdapter.get_available_tactics(distance)` 继续按距离窗口收缩可用模板；
5. 若当前模板仍满足保持条件，则优先保持，避免频繁切换；
6. 若当前模板已不适配，则切到更合适的攻击或防御模板。

因此，模板选择不是“一次查表就结束”，而是：

**态势形成 -> 候选收缩 -> 模板评估 -> 模板保持/切换**

这条真实链。

## Q43.2：当前模板选择为什么说是“风险区驱动”，而不是“意图驱动”？

**A：**

因为在正式主链里，真正最早、最稳定参与决策的是：

- 敌方在哪个风险区；
- 当前控制距离到了哪个节点；
- 当前几何是否适合继续压缩还是该止压；
- 当前双路分工是否还稳定。

这些信息比意图识别结果更早出现、更稳定、也更直接参与火力组织。

所以当前正式主链里，说“风险区驱动”更准确。

这并不否认意图识别价值，而是承认当前主链的真实优先级结构。

## Q44：原需求里不是说“根据意图识别选模板”吗，为什么现在不是这样？

**A：**

这是项目从理想化设计走向可执行实现后的重要调整。

原需求设计文档中，模板选择框架更理想化，强调：

- 态势评估；
- 威胁评估；
- 敌方意图识别；
- 再做模板选择。

当前实现中，这条链并没有被完全否定，但正式主链为了稳定性和实时性，优先采用了：

- 风险区判定；
- 控制距离节点；
- 当前目标几何与战术图；
- 模板规则保持。

意图识别当前仍然接入并运行，但更多承担：

- 中后段语义解释；
- 最高威胁目标注释；
- 复盘辅助说明。

因此，正式表达应该是：

**原设计给出的是完整理想框架，当前系统已经把主链稳定落地，而意图识别模块处于已接入、已运行、正在逐步增强其前端作用的阶段。**

## Q45：分层战术决策四层到底是什么？

**A：**

当前正确口径是四层：

### 1. 阶段决策层

并在交战阶段按控制距离节点推进。

### 3. 机动决策层

- 完成占位；
- 照射；
- 转换；

### 4. 参数决策层

- 脱离幅度；
- 发射门禁相关参数。

这个四层定义必须严格按当前项目来讲，不能混成别的版本。

## Q46：这四层真的在仿真中体现出来了吗？

**A：**

体现出来了，而且第六章正式综合验证就是在验证这四层有没有打通。

例如在正式仿真中可以看到：

- 阶段层通过 `PATROL / INTERCEPT / ENGAGE / EVADE / RTB` 以及 `NLT/MELD/MTR/LR/TR/DOR/DR/MAR` 推进；
- 战术层通过不同阶段的模板选择、左右路分工和模板保持体现；
- 机动层通过占位、照射、规避、再压缩等动作序列体现；
- 参数层通过航向/高度/速度微调、控制距离压缩速率和门禁节奏体现。

所以四层不是抽象管理学说法，而是有仿真证据支撑的。

## Q46.1：如果专家说“你说四层打通了，但我只看到结果，没有看到层间传递”，怎么回答？

**A：**

可以用“层间因果链”来答，而不要只说“接口打通”。

一个更强的回答方式是：

- 阶段层先决定当前是在 `PATROL / INTERCEPT / ENGAGE / EVADE / RTB` 哪个任务状态，以及双路当前处于 `NLT/MELD/MTR/LR/TR/DOR/DR/MAR` 哪个控制节点；
- 战术层在这个节点上决定当前左右路采用什么模板、谁是主攻、谁是支撑；
- 机动层把模板翻译成一串动作序列，例如前压、占位、照射、偏置、规避或回转；
- 参数层在执行前实时修正具体航向、高度、速度、偏置幅度和门禁阈值；
- 最终这些修正后的命令再通过低层控制链进入 JSBSim。

也就是说，层间传递不是抽象概念，而是：

**阶段给上下文，战术给组织方式，机动给动作语义，参数给执行幅度。**

这四层缺一不可。

## Q46.2：为什么说场景一、场景二、场景三分别从不同侧面验证了四层决策？

**A：**

因为三场景的关注点不同：

- 场景一更适合看四层是否完整闭合；
- 场景二更适合看受扰情况下四层能否继续协同推进；
- 场景三更适合看高风险低空突防下四层是否还能压缩链路、提前兑现、并在规避后保持主链。

所以三场不是重复验证，而是从：

- 完整性；
- 韧性；
- 前置性

三个维度验证四层决策体系。

## Q47：5.7 打断机制与参数自适应策略到底讲什么？

**A：**

5.7 讲的是：

- 当前模板和动作序列不是死板执行；
- 当传感器或威胁状态出现突变时，系统能否及时打断、止压、回退或改用更保守参数；
- 在保证生存性的同时，不把整条任务链完全打断掉。

它要解决的核心矛盾是：

**既不能一味硬打，也不能一遇威胁就彻底失去作战组织能力。**

## Q47.1：如果专家追问“打断机制和模板切换是什么关系，它们是不是一回事”，怎么回答？

**A：**

不是一回事，但高度相关。

- 打断机制回答的是：当前主链是否需要为了生存性暂时止压、回退或重组；
- 模板切换回答的是：在当前新约束下，应该改用哪种战术组织方式继续执行。

也就是说：

- 打断机制更像“是否要刹车”；
- 模板切换更像“刹完以后换哪条路继续走”。

两者顺序通常是：

威胁上升 -> 触发打断 -> 进入规避/保守状态 -> 重新评估 -> 保持或切换模板 -> 重接主链

这就是为什么在正式仿真里，经常会看到 `EVADE`、`DEFENSIVE_GUARD`、`ADAPTIVE_ATTACK` 这些现象前后关联出现。

## Q47.2：如果专家问“参数自适应到底适配了哪些参数”，怎么回答？

**A：**

当前最稳的回答，不是硬说成“在线优化了一个大全量参数向量”，而是明确指出它主要体现在以下几类参数风格的动态修正：

- 航向偏置幅度；
- 距离压缩节奏；
- 速度保持还是加速脱离；
- 规避后再压缩的进入时机；
- 门禁判断在高压窗口下的执行严格度。

这些调整不一定以“参数表第几项改了”这种形式暴露在日志里，但它们已经体现在：

- 控制距离推进曲线；
- 模板保持时长；
- `EVADE` 后的重接效率；
- 最小高度、最小速度、最小敌我距离这些结果量。

## Q48：打断机制真的触发过吗？

触发过，而且三次正式仿真都触发了。

## Q49：如果专家问“打断后是不是就乱了”，怎么回答？

**A：**

不能这么理解。

当前项目里的打断机制不是“失控中断”，而是“生存优先下的有组织切换”。

从三场正式样本可以看到：

- 场景一说明：打断不会过早破坏完整基线主链；
- 场景二说明：打断后仍能恢复长期压制；
- 场景三说明：高风险低空突防样本中，首轮兑现后能主动止压并守住主链。

所以，打断机制的价值不在于“是否打断”，而在于“打断后能不能重接链路”。

## Q49.1：参数自适应策略在正式仿真里体现在哪里？

**A：**

它不一定以“参数自适应”四个字直接出现在日志里，但它体现在多个结果量上：

- 控制距离压缩速率不是机械常数，而会随阶段和威胁变化；
- 航向偏置幅度会随战术阶段变化；
- 高压近距时门禁会从更严格条件向更可执行条件过渡；
- 规避后的再压缩也不是固定回到原路径，而是以当前威胁和几何重新组织。

在正式仿真中，如果系统每次都用同一幅度、同一路径、同一门禁去硬打，那么：

- 场景二在失配和高压窗口下会更容易断链；
- 场景三在低空突防样本里也更容易打过头或来不及止压。

当前三场结果表明它没有这样僵化运行，这就是参数自适应真正起作用的证据。

# 六、意图识别模块的真实定位

## Q50：意图识别模块到底有没有实现？

**A：**

有实现，而且已经接入当前项目链路。

关键实现入口包括：

当前后端使用的是 `bvr_intent_new` 路线，能够输出：

- 意图标签；
- 威胁等级；
- 置信度；
- 使用模型信息。

因此，不能说“意图识别没有实现”。正确说法是：

**意图识别模块已实现、已接入、已在线运行，但在当前正式主链中不是前端主驱动。**

## Q51：意图识别在当前系统里到底做什么？

**A：**

当前最准确的定位是：

**它主要承担中后段语义解释和目标级行为标注作用。**

具体作用包括：

- 给敌机打出攻击、防御、撤退、侦察等语义标签；
- 给当前最高威胁目标附加语义威胁解释；
- 为时间线、日志和复盘提供目标行为说明；
- 为后续进一步把它接到模板前端提供接口基础。

当前不应夸大地说“正式三场仿真就是靠意图识别驱动模板选择的”，这不符合代码事实。

## Q52：为什么你们 PPT 里讲了意图识别设计，但第六部分主验证里它不像主角？

**A：**

这是答辩中一定会被问的问题。

正确回答是：

“意图识别模块已经设计、实现并接入系统，正式仿真中也确实在线运行；但从当前三次正式样本看，前段交战主链主要由协同探测、控制距离节点、风险区和战术模板规则驱动，而意图识别更多承担中后段语义解释与辅助分析作用。这并不表示意图识别没有实现，而是说明当前主链已经具备较好的降级运行能力，同时该模块仍有继续向前端决策增强的空间。” 

这个回答兼顾了真实性和项目价值，不会把自己逼进“要么全靠它、要么完全没用”的两难境地。

## Q53：为什么三次正式仿真里意图识别结果都很晚？

**A：**

这是当前架构下的正常现象，原因主要有三层。

### 第一，触发时机本身就不早

当前意图识别不是一开局就对所有目标裸跑，而是在进入相应战术阶段后，由任务链触发更新。

### 第二，它依赖决策态势图

它不是直接读取真值目标，而是基于当前 `decision picture` 中的有效威胁目标做识别。

### 第三，它有时序窗口 warmup

当前模型需要一段长度的序列窗口累积后，才会输出真正有效的分类结果。

所以，意图识别天然更像中后段模块，而不是开局 10 秒内就能成熟输出的前置模块。

## Q54：三次正式仿真里的意图识别数据怎么理解？

**A：**

### 场景一

- 首次意图接触：`620.4 s`
- 首次意图 ready：`620.4 s`
- 首次高威胁意图：`830.6 s`

说明它在场景一主要服务于中后段态势解释。

### 场景二

- 首次意图接触：`510.2 s`
- 首次意图 ready：`510.4 s`

说明它在场景二主要服务于持续压制阶段的目标行为语义判读。

### 场景三

- 全程无有效意图输出

但场景三主链仍然完整跑通，说明当前主作战链对意图识别不敏感，具备降级运行能力。

## Q55：那意图识别是不是没什么用？

**A：**

不能这么说。

更准确的表达是：

- 当前它不是前段主驱动；
- 但它已经具备在线运行和语义输出能力；
- 在中后段目标行为解释、日志标注和复盘中有实际价值；
- 未来完全可以进一步前推到模板选择或规避判断增强中。

换句话说，它当前是“已接入的增强模块”，而不是“未实现的摆设模块”。

## Q55.1：如果专家追问“那它未来最合理的增强方向是什么”，怎么回答？

**A：**

最合理的方向不是把它强行变成唯一主驱动，而是逐步前推它的影响范围。

可以分三步增强：

1. 继续保持当前目标级语义解释和复盘辅助角色；
2. 在模板选择阶段把它作为一个附加约束或偏好项，而不是唯一条件；
3. 在高威胁中后段，把它和威胁等级、传感器状态一起用于规避/回转/再压缩增强判断。

这样做更稳，也更符合当前系统的成熟度。

## Q56.1：如果专家问“这些图表和表格的数据到底来自哪里”，怎么回答？

## Q56.2：如果专家问“你们 PPT 上一个事件型指标到底该读 `count` 还是 `final_value`”，怎么回答？

**A：**

这个一定要说清。

尤其在 `event_counts.csv` 这类表里：

- `count` 表示“累计值发生了多少次跳变”；
- `final_value` 表示“最终累计到了多少”。

因此，如果你回答的是：

- 最终一共通过了多少次门禁；
- 最终一共成功了多少次接力；
- 最终一共发生了多少次事件；

你就不能机械地读 `count`，而应该读：

- `final_value`
- 或直接读 `summary.json` / `summary_metrics.csv` / `cooperative_chain_metrics.csv` 里的汇总值。

否则就会把“跳变次数”错说成“最终次数”。

## Q58.1：如果专家问“除了协同探测恢复，场景二还能说明哪些方法是有效的”，怎么回答？

**A：**

场景二不只是证明“看回来了”，它还验证了另外三层东西：

### 第一，模板体系不是脆弱脚本

如果模板体系是死板脚本，那么外层预警一受扰、几何关系一变化，主链就容易散掉。场景二没有散，说明模板保持、模板切换和双路骨架仍然有效。

### 第二，打断机制不是单向退缩

场景二里不是“受扰 -> 规避 -> 结束”，而是“受扰 -> 接手 -> 建稳 -> 发射 -> 规避 -> 再组织 -> 再压制”。这说明打断机制能和后续模板重接配合工作。

### 第三，参数自适应不是纸面设计

如果压缩节奏、门禁严度和再压缩时机都不调整，场景二这种高压受扰样本要么容易抢跑，要么容易断链。当前样本没有出现这种典型失控，这就是参数自适应有效性的侧证。

## Q59：场景三验证的核心是什么？

**A：**

场景三核心验证的是：

**高风险低空突防背景下的前置接手、快速减威和主链降级运行能力。**

场景三不是普通前压样本，而是带有明显低空突防特点：

- 威胁来得更快；
- 压力更早；
- 决策窗口更短；
- 对感知、模板、门禁、规避和再组织要求更高。

在这种情况下，系统仍然能：

- 快速建立稳定交战准备；
- 提前打开首轮攻击链；
- 在规避和再组织中维持主链；
- 最终完成清场。

这说明方法不只适用于“中规中矩”样本，也能适应高压突防样本。

## Q59.1：如果专家继续追问“场景三为什么一定要强调低空突防，而不是普通高风险”，怎么回答？

**A：**

因为低空突防和普通高风险样本不一样，它对系统提出的是另一类压力：

- 探测链更容易受下视、杂波和几何压缩影响；
- 目标更快逼近高风险区；
- 我方决策窗口更短；
- 模板不能靠长时间铺开来慢慢组织；
- 发射后也更容易立刻进入生存压力段。

所以场景三真正说明的是：

**这套方法不只会在“信息充分、节奏舒展”的样本里工作，还能在低空、快节奏、前置高压的突防样本里保持可执行性。**

## Q59.2：如果专家问“场景三里最能体现你们整套方法价值的，不是战果，而是什么”，怎么回答？

**A：**

最能体现价值的不是“最后打掉了几架”，而是：

- 感知链没有因为节奏快而来不及接手；
- 模板组织没有因为压力高而彻底失序；
- 首轮窗口兑现后系统能主动止压而不是盲目硬追；
- 即便意图识别没有形成有效输出，主链仍能闭合。

这说明你的主方法链具有较好的**前置执行性**和**降级运行能力**。这两点比单纯战果更能说服专家。

## Q60：场景二里预警信息失配到底说明了什么？

**A：**

场景二里最关键的不是“掉了多久”，而是：

**外层预警链失配后，系统有没有靠协同探测和机载链把主链接住。**

当前文档应重点强调首轮失配窗口及其恢复逻辑，而不是把所有周期性失配都展开。这样更符合汇报重点，也更容易形成清晰证据链：

- 首轮预警链失配；
- 模式切换；
- 机载雷达接手；
- 目标补齐；
- 稳定交战就绪恢复；
- 后续交战链继续推进。

## Q61：场景三除了“打得快”，还能证明什么？

**A：**

场景三能证明三件更深层的事：

- 第一，系统对高风险低空突防样本具备前置处理能力；

所以场景三不能只讲“打赢了”，更要讲“为什么在更难条件下还打赢了”。

# 九、与原需求的差异、局限与后续工作

## Q67：当前实现和原需求最大的差异是什么？

**A：**

最大的差异有三点。

### 第一，模板选择主驱动不同

原需求更强调“态势-威胁-意图”三位一体驱动模板选择。当前正式主链更强调：

- 风险区；
- 控制距离节点；
- 态势图几何；
- 模板规则保持。

### 第二，优化器表达和在线实现不同

原需求常用全局优化语言表述。当前实现保留其思想，但在线主要采用：

- 分层近似求解；
- 规则门控；
- 几何解析；
- 离散动作执行。

### 第三，意图识别的在线角色不同

原需求把它放在较前的高层决策输入位置。当前实现中，它已接入，但正式主链里更偏中后段语义解释。

这三点不是“失败”，而是“从理想框架到可运行系统”的正常落地调整。

## Q68：当前项目的主要局限是什么？

**A：**

可以诚实但积极地讲三点：

- 第一，意图识别模块已实现，但当前在正式主链中尚未成为前段主驱动；
- 第二，模板选择目前仍以规则链为主，尚未引入更强的自适应元战术层；
- 第三，综合验证样本已经具备代表性，但仍可进一步扩展更多敌方复杂机动和更多随机种子。

这种回答既诚实，又不会把项目说成“不成熟”，而是指出清晰可扩展方向。

## Q69：后续工作最值得做什么？

**A：**

最有价值的后续方向包括：

- 把意图识别从中后段解释模块进一步前推到模板选择增强模块；
- 在战术层之上增加更强的元战术选择层；
