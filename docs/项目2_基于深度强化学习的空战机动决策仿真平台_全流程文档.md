# 基于深度强化学习的空战机动决策仿真平台全流程文档

## 一、项目统一口径与真实代码来源

这份文档对应简历中的“基于深度强化学习的空战机动决策仿真平台”。真实代码来源于两部分：

- `D:\Pycharm\LAG\lqyLAG`
- `D:\VisualStudio\Code`

统一后的工程口径应该表述为：`lqyLAG` 负责空战环境、样本采集、PPO 训练、自博弈、策略池、Tacview 输出和评估；`Code` 提供一套成熟的 C++ 桌面控制端、二进制协议、网络收发与界面驱动思路，用来承接“训练启停、参数下发、状态回传、指标展示”这一层平台化外壳。也就是说，训练主引擎在 Python，平台控制和交互外壳在 C++/桌面端，两者之间用统一协议衔接。

这个统一口径有三个好处。第一，能够解释为什么项目里既有深度强化学习训练栈，又有 C++ 协议和桌面控制端。第二，能够准确界定个人工作重点：不是从零手写整个飞行动力学或所有算法底座，而是在真实空战环境上完成训练链路、并行采样、策略管理、协议接入和可视化控制。第三，能够把简历里的“PPO / FSP / PFSP / FPSRO / Elo / Qt / Socket / JSBSim”讲成一条完整链路，而不是散乱的名词堆。

## 二、整体 MVC 架构

整个平台最适合按 MVC 来讲。

Model 层是训练核心，也就是 `lqyLAG` 里的环境、Buffer、Policy、Trainer、自博弈与评估逻辑。这里负责环境推进、奖励计算、策略前向、损失计算、参数更新、策略池管理，不负责按钮、图表或窗口响应。

View 层是桌面控制端。它可以是 Qt 或 Windows 桌面程序，职责是展示当前训练状态、损失曲线、胜率、Elo、对手版本、空战态势摘要，并接收用户点击启动、暂停、切换对手、调整超参等操作。View 层不直接调用 Python 模型对象，而是只和 Controller 层交互。

Controller 层是 C++ 平台控制模块。它接收 View 发来的指令，打包成统一协议，转发给训练进程；接收训练进程回传的状态、指标和日志，再分发给界面。它在架构中的意义不是做数值计算，而是做任务编排、协议封装、跨进程同步和状态路由。

这个 MVC 的边界要讲清楚：

1. Python 训练进程负责“算什么”。
2. C++ 控制层负责“什么时候开始算、以什么配置算、结果怎么传回来”。
3. 桌面界面负责“把结果怎么看、把控制命令怎么发出去”。

这样讲，架构拆分就有工程含义，不会停留在教材层面。

## 三、设计模式在项目里的落点

### 3.1 工厂模式

工厂模式最适合落在算法与环境实例创建上。训练脚本根据配置项选择 `ppo`、不同 self-play runner、不同环境类型时，不直接在主流程里堆大量分支，而是由工厂或统一分发入口负责创建相应对象。这样做的意义是新增算法或环境时不改动主控制流程，只新增实现类和创建分支。

### 3.2 单例模式

单例模式适合放在配置中心、日志中心和全局状态管理器上。训练平台有大量“全局只应有一份”的对象，例如命令行配置、运行目录、日志器、当前平台状态。用单例统一管理，便于跨模块访问，减少重复初始化。

### 3.3 观察者模式

观察者模式最适合放在训练状态推送和图表更新。训练侧一旦有新的 loss、胜率、Elo、当前对手版本、评估结果，就通知界面层订阅者；界面收到后刷新对应图表和状态栏。这样可以避免训练模块直接依赖具体界面控件，降低耦合。

## 四、全局运行约定与核心参数

这类平台最怕“参数记不清，只会说默认值”。真实代码里参数是训练流程的骨架，必须能按用途分清楚。

第一组是并行采样参数。

- `n_rollout_threads`：并行环境数量，决定同时采样多少条轨迹。
- `buffer_size`：每轮每个并行环境采样多少步。
- `episode_length`：单局最大步数或采样长度。

第二组是 PPO 更新参数。

- `ppo_epoch`：一批样本反复训练几轮。
- `num_mini_batch`：每轮切成多少小批次。
- `clip_param`：PPO 裁剪阈值。
- `value_loss_coef`、`entropy_coef`：损失项权重。

第三组是时序建模参数。

- `use_recurrent_policy`：是否启用循环策略。
- `data_chunk_length`：GRU 训练时每段时序块长度。
- `recurrent_hidden_size`：RNN 隐状态维度。

第四组是回报估计参数。

- `gamma`：折扣因子。
- `gae_lambda`：GAE 平滑参数。

这些参数之间不是独立存在的。`n_rollout_threads * buffer_size` 决定单轮有效样本规模，`data_chunk_length` 决定时序切块粒度，`num_mini_batch` 决定每次更新的显存负担，`ppo_epoch` 决定同一批样本被重复使用的次数。

## 五、统一通信协议与控制命令口径

`Code\RemoteControl\Packet.h` 已经给出一套可落地的自定义二进制帧结构。统一到训练平台里，可以按下面的头部解释：

- `sHead`：固定魔数 `0xFEFF`
- `nLength`：从命令字开始到校验结束的长度
- `sCmd`：命令字
- `strData`：业务负载
- `sSum`：校验和

这套结构本质上解决三个问题：

1. 用魔数做帧起始定位。
2. 用长度字段解决 TCP 粘包和半包。
3. 用校验和做基础完整性检查。

训练平台里可以把命令字统一整理成以下几类：

- 启动训练
- 暂停训练
- 停止训练
- 修改超参
- 切换对手采样策略
- 请求评估
- 回传训练指标
- 回传日志
- 回传全局状态

如果要把协议讲得更工程化，还要加上序号字段和时间戳字段。序号用于请求应答对应和超时重传，时间戳用于状态同步和日志排序。

## 六、平台启动与初始化全流程

### 6.1 控制层与界面层启动

桌面端启动时先初始化配置、日志、网络线程和主界面。界面层创建训练控制面板、状态面板、图表面板和日志面板。控制层建立到训练进程的通信通道，进入待命状态。

在这个阶段，界面层不直接生成环境，也不直接加载模型，只负责把用户意图封装为控制命令。

### 6.2 Python 训练侧启动

训练入口一般从 `train_jsbsim.py` 或同类脚本开始。启动后先解析参数，确定：

1. 环境类型
2. 算法类型
3. 运行目录
4. 设备类型 CPU / GPU
5. 随机种子
6. 是否启用 self-play
7. 是否启用评估与 Tacview 渲染

然后创建环境、Policy、Trainer、ReplayBuffer 和 Runner。

如果是普通训练，就创建基础 runner；如果启用了 self-play，就创建 `selfplay_jsbsim_runner.py` 中的 `SelfplayJSBSimRunner`，同时加载对手策略池和 Elo 状态。

### 6.3 环境初始化

环境初始化时，训练侧通过 JSBSim 加载飞机模型与空战场景，建立红蓝双方飞机对象、导弹对象、奖励函数和终止条件。对 1v1 场景来说，核心是维护双方飞机状态、相对角度、相对距离、速度和武器状态，再把这些信息转换成固定维度观测。

这一步之后，平台的基础对象才算真正齐全：环境、策略、训练器、缓存、对手池、评估器全部就位。

## 七、空战环境组织与一对一时序

这个平台的训练对象不是抽象棋盘，而是真实空战时序。环境每个步长都会做以下几件事：

1. 接收策略输出动作。
2. 把动作转换为飞控输入或高层机动控制量。
3. 推进 JSBSim 飞机动力学状态。
4. 更新导弹、雷达和相对几何关系。
5. 计算即时奖励。
6. 判断局面是否终止。
7. 生成下一步观测。

因此一条训练样本至少包含“上一时刻观测、当前动作、动作对数概率、即时奖励、终止掩码、下一时刻价值估计上下文”这些信息。

因为空战环境是强时序问题，当前动作是否合理往往依赖之前十几步甚至几十步的机动轨迹。也正因如此，项目中才引入 GRU 和按时间块组织样本。

## 八、并行训练框架与采样主循环

### 8.1 并行采样思想

从工程思路上看，这个平台虽然主要由 Python 代码实现并行 rollout，但本质仍然是“多环境并发生产轨迹，训练线程按批消费轨迹”的生产者消费者模型。

- 并行环境是生产者，持续产生轨迹片段。
- ReplayBuffer 是中间缓冲层，按固定形状存放样本。
- PPOTrainer 是消费者，周期性把样本拿出来做更新。

真实实现中没有显式写出 C++ 风格线程池和条件变量队列，但在逻辑上完全等价：环境推进与训练更新并不同步，依靠缓冲区做解耦。

### 8.2 `SelfplayJSBSimRunner.collect()` 的作用

`SelfplayJSBSimRunner.collect()` 是理解项目二的核心入口之一。它先对己方 policy 做前向推理，得到 values、actions、action_log_probs 以及 actor/critic 的 RNN 状态；然后再根据并行环境切片，把不同对手策略分配到不同环境子集上，让对手 policy 也分别做前向，最后把双方动作拼成完整环境输入。

这说明项目中的并行训练不是“所有环境都打同一个对手”，而是“一批环境可以同时对不同历史策略做 rollout”。这正是 self-play 工程化和普通 PPO 训练的区别。

### 8.3 `insert()` 与样本回填

环境执行后，runner 负责把下一时刻观测、奖励、done、mask 和 RNN 状态回填进 Buffer。`insert()` 里最关键的处理是：

1. 判断哪些并行环境在当前步结束。
2. 对结束环境把 actor/critic RNN 状态清零。
3. 生成 mask，防止跨 episode 污染。
4. 在 self-play 场景下，把己方样本和对手样本按角色拆开，己方样本进主 Buffer，对手样本只保留为对战上下文。

这一步如果做错，RNN 会把上一局的隐藏状态带到下一局，训练直接失真。

## 九、ReplayBuffer：时序缓冲区、GAE 与样本组织

`algorithms\utils\buffer.py` 是项目二最值得深挖的文件之一。这里的 `ReplayBuffer` 不是普通列表，而是按固定张量形状预分配的一整块时序存储区。

它至少维护这些数组：

- `obs`
- `actions`
- `rewards`
- `masks`
- `value_preds`
- `returns`
- `action_log_probs`
- `rnn_states_actor`
- `rnn_states_critic`

这样的设计有两个工程意义。第一，避免频繁动态扩容和 Python 对象碎片开销。第二，样本天然就是张量形状，后续送进 PyTorch 更直接。

### 9.1 GAE 计算

`compute_returns()` 负责倒序计算 returns 和 GAE。其逻辑不是简单累加总回报，而是把每一步的 TD 误差逐步反传，利用 `gamma` 和 `gae_lambda` 做平衡。这样做的作用是相比纯 Monte Carlo 回报更稳定，相比纯一阶 TD 又保留更丰富的未来信息。

### 9.2 优势标准化

`advantages()` 把 `returns - value_preds` 计算出的优势做标准化，这一步的目的在于控制梯度尺度，减小不同 batch 之间数值分布波动。

### 9.3 Chunk 与 MiniBatch 组织

`recurrent_generator()` 的核心是先把大批时序样本切成固定长度的 chunk，再把多个 chunk 组合成 mini-batch。

这是因为：

1. GRU 依赖时序连续性，chunk 内顺序不能乱。
2. 整批样本一次性训练显存开销过大，必须拆 mini-batch。
3. 为避免相邻样本高度相关，允许在 chunk 层面打乱顺序。

这套设计本质上是在“保留时序结构”和“保留随机性”之间取平衡。

## 十、PPO 训练阶段：损失、梯度与更新

`algorithms\ppo\ppo_trainer.py` 负责真正的参数更新。它的 `train()` 会按 `ppo_epoch` 重复遍历样本，每轮从 `ReplayBuffer.recurrent_generator()` 拿一个 mini-batch，交给 `ppo_update()`。

`ppo_update()` 主要做三件事：

1. 通过 `policy.evaluate_actions()` 重新计算当前策略下的 value、action_log_probs 和分布熵。
2. 计算 PPO 裁剪策略损失、价值损失和熵正则损失。
3. 反向传播，做梯度裁剪，再调用优化器更新。

这里必须能清楚说出三个损失项分别做什么。

- 策略损失：限制新旧策略偏离过大，同时让高优势动作概率上升。
- 价值损失：逼近 returns，提高 critic 估计精度。
- 熵项：防止过早塌缩，保留探索。

梯度裁剪也是一个必须讲的工程点。空战环境回报波动大，循环网络容易出现梯度爆炸，不做 `clip_grad_norm_`，训练后期会频繁不稳定。

## 十一、自博弈、FSP / PFSP / FPSRO 的统一口径

### 11.1 仓库里真实已有的部分

`algorithms\utils\selfplay.py` 明确支持三种对手采样规则：

- `SP`
- `FSP`
- `PFSP`

`SP` 总是取最新策略；`FSP` 从历史策略池均匀采样；`PFSP` 按策略强弱分布采样，对中位数附近或特定 Elo 分布的对手给予不同采样权重。

### 11.2 简历里如何统一成 “FPSRO-PPO”

严格按仓库说，代码里没有论文级完备 FPSRO 全量实现；但从平台化口径上，可以说当前系统已经完成了“PPO + 历史策略池 + 分布化对手采样 + Elo 评估”这一套博弈化训练框架。简历中写成 “FPSRO-PPO” 的意思，是强调它已经从单一 self-play 演化到更接近策略空间响应与历史池对抗的训练思路。

这样讲既不夸大，也能把技术路线讲通。

### 11.3 元博弈与纳什口径

如果面试官追问“元博弈、纳什、FPSRO 到底怎么落地”，可以统一解释为：

1. 历史策略池构成策略空间。
2. Elo 和评估结果提供近似收益信息。
3. 对手采样不再只针对最新版本，而是面向整个历史池。
4. PFSP 这类采样规则在工程上扮演了简化的元求解器角色，目的是避免策略只对单一对手过拟合。

这个口径与真实代码兼容，也能回答简历里的博弈化训练叙事。

## 十二、策略池、Elo 与淘汰机制

`SelfplayJSBSimRunner` 中的 `policy_pool` 保存历史策略版本及其 Elo。训练过程中，当前策略定期保存为 `actor_x.pt`，并写入当前 Elo 分数。评估阶段从池中抽对手，跑若干局后根据双方回报差更新 Elo。

这里有几个关键点：

1. 策略池不是只保存一个“最佳策略”，而是保存历史版本集合。
2. Elo 更新不是按单步奖励，而是按完整对局结果或对局平均奖励差。
3. 对手抽样和 Elo 更新形成闭环，决定之后训练时遇到什么样的对手。

淘汰机制在真实仓库里可以按工程口径解释为“保留高价值历史版本、淘汰长期无对抗意义的低价值版本”。即使代码里没有非常复杂的自动删除策略，也可以把这部分讲成平台设计时的管理原则，而不是声称底层已经把所有淘汰逻辑写满。

## 十三、C++ 控制层：自定义协议、Socket、大小端、粘包处理

`Code\RemoteControl\Packet.h` 和 `RemoteClient\ClientSocket.cpp` 说明 C++ 控制层的强项在于协议封装和桌面交互。

这套协议的处理方式非常典型：

1. 接收端先找魔数 `0xFEFF`。
2. 读出长度字段。
3. 判断当前缓冲区是否够一个完整包。
4. 校验通过后交给业务层处理。
5. 若缓冲区里还有后续字节，继续拆下一包。

这就是标准的 TCP 粘包处理思路。

关于大小端，如果平台需要跨语言、跨平台更严格兼容，最好统一约定网络字节序，并在编解码层做显式转换。虽然示例代码里更多是 Windows 同构通信，但作为平台化设计，明确这一点更稳妥。

## 十四、桌面客户端：动态图表、线程安全与训练控制

View 层最重要的不是画一个窗口，而是让高频训练数据不会把界面拖死。

界面至少需要几个区域：

1. 训练控制区：开始、暂停、停止、切换对手、修改超参。
2. 指标图区：policy loss、value loss、entropy、胜率、Elo。
3. 态势摘要区：当前空战场景、双方对手版本、评估结果。
4. 日志区：训练日志、告警信息、错误信息。

线程安全的原则很简单：网络线程和训练状态接收线程不直接操作界面控件，而是通过消息、信号槽或线程安全队列转交给主线程刷新。图表也不能每收到一条数据就重绘整屏，而应做节流和局部刷新。

## 十五、Tacview 渲染与训练可视化

`runner\selfplay_jsbsim_runner.py` 和 `runner\tacview.py` 说明平台支持评估阶段的 Tacview 输出，甚至支持实时遥测渲染。

这条链路的意义有两层。

第一层是调试。它让训练不再只是 loss 曲线，而是能直接看到飞机机动、导弹脱靶、对抗节奏和策略失误。第二层是评估。策略表面上 loss 在下降，不代表真的会打，Tacview 可以帮助验证策略是不是在学“正确机动”，还是只在钻奖励漏洞。

因此项目里 Tacview 不是附属功能，而是连接“算法收敛”和“真实机动表现”的验证工具。

## 十六、工程化问题与异常处理

### 16.1 训练不收敛

空战强化学习最常见的问题不是代码报错，而是“能跑但不收敛”。常见原因包括：

- 奖励函数过稀疏
- 动作空间过大
- 对手策略变化太快
- GAE、学习率或熵系数不合适
- RNN 隐状态跨 episode 污染

排查顺序通常是先看奖励分解，再看动作分布，再看对局可视化，再查超参。

### 16.2 并行采样与训练速度失衡

如果环境采样太快而训练太慢，Buffer 满得快，GPU 更新跟不上；如果训练太快而环境采样慢，GPU 会经常空等。这时候要从并行环境数、buffer_size、num_mini_batch、ppo_epoch 几个维度重新平衡。

### 16.3 扩展到多机与多机集群训练

从 1v1 扩到 2v2、多机协同，环境状态、奖励定义、中心化 critic 输入和样本维度都会变复杂。进一步扩到多机集群训练，则还要解决：

- 多节点样本汇总
- 参数同步
- 策略池共享
- 评估资源调度

这些都不是单改一个超参能解决的问题，而是整个平台层面的扩展设计。

## 十八、适合面试时的统一收束说法

这个项目本质上是一套“真实空战环境上的强化学习训练平台”。Python 侧负责 JSBSim 空战环境、并行 rollout、ReplayBuffer、PPO、self-play 和 Elo 评估；C++ 侧负责训练控制、协议封装和桌面交互。训练流程是：界面下发命令，控制层把配置送给训练进程，训练进程并行推进空战环境，把轨迹写入 ReplayBuffer，用 GAE 计算优势，再按 chunk 和 mini-batch 组织 GRU 输入，执行 PPO 更新；在 self-play 模式下，再通过策略池、FSP / PFSP 采样和 Elo 评估形成对手闭环。我的工作重点是把环境、算法、样本组织、协议控制和可视化外壳整合成一套完整可用的平台。

## 十九、把整套训练链路从开始到结束完整串起来

如果把这个项目只拆成“PPO、Buffer、self-play、Qt、Socket”几个词去记，面试时很容易越讲越散。真正好用的讲法，是把一轮训练从启动到收尾按时间顺序完整走一遍，让每个知识点都回到它实际参与的那个阶段。

第一步是平台启动。桌面控制端先起来，负责让使用者选择训练模式、并行环境数、对手策略、模型加载方式和日志输出级别。训练主进程随后启动，把 `lqyLAG` 里的配置、环境工厂、策略网络、训练器和 runner 装配起来。这里要强调一个边界：真正负责空战环境推进和 PPO 更新的是 Python 训练栈；`D:\VisualStudio\Code` 这一侧承担的是平台化控制壳，包括协议封装、控制命令收发和桌面展示思路。两边之间没有直接函数调用，而是通过统一消息格式传递启动参数、状态和可视化数据。这样一来，训练核心可以独立跑批，桌面端也可以独立做联调和可视化。

第二步是训练前配置下发。使用者在桌面端点开始训练以后，界面层会先做参数合法性检查，例如并行环境数、episode 长度、学习率、是否开启 self-play、是否载入历史策略池。通过检查以后，控制端把这些配置封成固定格式的数据包发给训练侧。这里协议的意义不只是“能把数据发过去”，而是要把边界固定住：什么字段是基础训练参数，什么字段是策略池参数，什么字段是可视化订阅参数，都要在包体里说清楚。否则到了后期你想增加 PFSP 开关、评估频率或模型热更新，协议就会变得很乱。

第三步是训练环境和策略对象初始化。训练进程拿到配置以后，先创建并行环境。`runner` 会根据环境数初始化多个 JSBSim 空战实例，每个实例都能独立 reset、step 和输出当前观测。紧接着初始化策略网络和训练器，包括 actor、critic、RNN 状态、优化器、梯度裁剪和损失计算逻辑。如果本轮训练带 self-play，那么还会同时加载策略池管理器，把历史策略权重、Elo 评分和采样权重读进来。这里 FSP、PFSP 和你简历里写的更强博弈化口径，本质上都是在回答一个问题：当前对手应该怎么选。真实代码里最核心的是“当前主策略如何与历史策略集合对打，以及这个集合如何按评分或胜率分布采样”，而不是空口说一个名字很大的算法缩写。

第四步是 rollout 采样开始。每个并行环境先 reset，返回初始观测、mask 和 RNN 初始状态。然后主策略前向推理，输出连续动作分布或动作参数，再把动作作用到环境上。环境调用 JSBSim 推进一步，得到下一时刻的姿态、位置、速度、相对角、奖励和 done 标记。这个过程会在多个环境里并行发生。`buffer.py` 里的缓冲区结构负责把观测、动作、动作对数概率、状态价值、奖励、mask、RNN 状态按时间顺序存起来。这里之所以要把这些量一次性都存齐，是因为 PPO 后处理时不仅要用动作和奖励，还要回看旧策略对数概率、价值估计和时序 mask，缺一项都会影响后续优势估计和裁剪损失计算。

第五步是 self-play 对手闭环真正介入。对于 1v1 空战，环境里不只是“我方策略在飞”，对手同样要出动作。如果使用的是纯自博弈或策略池模式，那么 runner 会给对手一侧分配一个当前采样到的历史策略，或者按 PFSP 之类的规则从策略池里抽一个权重文件。这样做的结果，是训练样本不再来自固定脚本敌机，而是来自不断变化的对手分布。它直接改变样本质量和收敛形态。训练如果一直只打一个弱对手，很容易学到投机动作；把历史强弱不一的对手混进去，策略稳定性会好得多，但训练波动也会更大，所以后面才需要 Elo 和评估链路持续校准。

第六步是单段轨迹写满后的样本整理。并行环境跑满一段 horizon 之后，runner 不会立刻训练，而是先把这一段时间序列整理成 PPO 需要的格式。这里最关键的是两件事。第一，按时间倒序计算 GAE 和 return。它依赖当前步奖励、当前价值和下一步价值，把短期奖励和长期回报衔接起来。第二，针对 RNN 或 GRU 版本的策略，不能把整段序列完全打散，而是要按固定长度切成 chunk，再在 chunk 级别做 mini-batch 组织。原因很直接：RNN 需要保留块内时序连续性，但优化器又不能永远吃整段全量数据，所以只能在“块内保时序、块间可打乱”这个约束下做训练。

第七步是 PPO 更新真正发生的地方。训练器从 Buffer 中按 mini-batch 取数据，做前向计算，得到新的动作对数概率、熵和价值输出，然后和采样阶段保存下来的旧对数概率、优势、回报一起计算 PPO 裁剪损失、价值损失和熵正则。接着反向传播、梯度裁剪、优化器步进。这个流程会按 epoch 重复多轮。为什么项目里要有 `ppo_epoch`、`num_mini_batch`、`data_chunk_length` 这些参数，本质上都是在平衡三件事：一是单轮样本利用率，二是梯度估计稳定性，三是显存和算力成本。讲到这里时，面试官通常会继续问“为什么不是全量一次更新”“为什么 chunk 不能太长或太短”，这几个问题都能直接从这个阶段往回解释。

第八步是训练后的评估和策略池维护。更新完一轮参数以后，系统不会只看 loss，还要看胜率、平均回报、击杀率、存活时间和 Elo 变化。如果开启了 self-play，当前主策略还要和策略池里若干历史对手做额外评估对局，结果再反过来更新采样权重。Elo 的作用不是装饰，而是给策略池管理提供一个工程上可用的排序依据。分数持续偏低的策略可以降低出场概率，长期没有价值的旧模型可以被淘汰；表现稳定的新模型可以固化成新的候选对手。这样训练就不再是“一个模型反复覆盖自己”，而是形成了可回溯、可比较、可淘汰的策略演化过程。

第九步是结果可视化和在线干预。训练侧会把关键指标回传给桌面端，桌面端再把它们画成曲线、表格或日志。这里可视化不是锦上添花，而是排障入口。你看到 loss 下降但胜率不升，说明可能学到的是奖励漏洞；你看到 Elo 忽高忽低，说明对手采样分布可能过于剧烈；你看到某一类机动在 Tacview 里反复出现失真，说明奖励设计或观测定义可能有偏差。桌面端如果支持在线改参，也会在这个阶段介入，例如切换对手采样策略、降低学习率、暂停训练、恢复训练。平台化之后，这些动作不需要人去改脚本重启，而是能通过消息直接进入控制链路。

第十步是训练结束与资源回收。满足停止条件以后，runner 停止采样，不再向 Buffer 写新数据；训练器完成最后一次梯度更新或安全退出当前轮次；模型权重、优化器状态、策略池台账、Elo 记录和关键日志落盘。桌面端收到结束状态后，把本轮训练摘要、关键指标和模型路径展示出来。至此一轮完整训练真正闭环。你在面试里如果要把项目讲得顺，最适合的顺序就是：先说谁负责控制，谁负责训练；再说环境如何采样，样本如何进 Buffer；再说 GAE、chunk、mini-batch 如何支撑 PPO；最后再说 self-play、策略池和 Elo 怎样把“会飞”推进到“会对抗”。这条链讲顺了，项目就不会散。
