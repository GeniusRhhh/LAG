# 基于 FFmpeg 的多功能直播平台全流程文档

## 一、项目统一口径与真实代码来源

这份文档对应简历中的“基于 FFmpeg 的多功能直播平台”。真实代码来源于：

- `D:\VisualStudio\EPlayerServer`
- `D:\VisualStudio\ENET`

统一后的工程口径是：`EPlayerServer` 负责 HTTP 业务接入、登录鉴权、数据库访问、线程池、日志和主从进程架构；`ENET` 负责 RTMP 媒体服务、信令控制、自定义网络层和客户端推拉流端。组合之后，可以讲成一套完整的直播平台：客户端完成采集、编码、推流、拉流和播放，服务端完成登录、房间、流分发、数据库持久化和运行监控。

这里一定要把边界讲实。FFmpeg、http-parser、MySQL、SQLite、RTMP 协议不是从零发明，项目工作的重点是把这些底层能力以统一线程模型、统一协议边界和统一业务流程组织起来，并把登录、房间、推拉流、索引、回放、监控这几条链路打通。

## 二、总体架构：业务层、信令层、媒体层

从运行形态看，平台可以分为三层。

第一层是业务层，对应 `EPlayerServer`。它负责 HTTP 请求接入、登录请求解析、签名校验、数据库查询、房间与用户记录、日志输出和后台运维接口。

第二层是信令层，对应 `ENET\SigServer`。它负责房间创建、成员加入、推流端与播放端角色管理、流地址下发、断开通知和一推多拉关系的业务组织。

第三层是媒体层，对应 `ENET\RtmpServer` 和客户端推拉流模块。它负责 RTMP 握手、Chunk 解析、Message 分发、Session 组织和媒体转发。

这种分层非常适合直播场景。业务层关心的是谁可以开播、谁能进房、直播间状态是什么；信令层关心的是房间里谁是主播、谁是观众、该推哪一路流、该拉哪一路流；媒体层只关心收到的 H.264 / AAC 包怎样进来、怎样分发出去。

## 三、服务端主从 Reactor 与多线程模型

### 3.1 `EPlayerServer` 的主进程、多线程结构

`EPlayerServer` 不是单线程 HTTP demo，而是按“主进程 + 业务子进程 + 日志子进程”组织。

- 主进程负责监听端口和接收新连接。
- 业务子进程负责具体业务处理。
- 日志子进程负责统一写日志。

`CServer.cpp` 可以看出这条链路：先绑定业务入口函数，再创建业务子进程，再启动线程池和 epoll，最后把监听 socket 加入 epoll。主进程中的线程池工作线程阻塞在 epoll 上，一旦有新连接就接收客户端，再通过进程间通信把客户端 fd 交给业务子进程处理。

这套结构的意义在于：

1. 把接入层和业务层隔离。
2. 把日志落盘与业务处理隔离。
3. 用多线程处理 epoll 事件，提高并发能力。

### 3.2 主从 Reactor 统一口径

虽然代码不是严格套某个框架名，但从设计口径上完全可以统一成主从 Reactor。

- 主 Reactor：监听 socket，负责 accept 新连接。
- 从 Reactor 或业务线程：处理已建立连接上的读写事件、HTTP 解析和业务逻辑。

这样讲的好处是可以直接回答“为什么不是一个线程全做完”。因为 accept 新连接和处理复杂业务放在一个事件循环里，容易导致监听层被业务阻塞。拆开之后，接入和业务互不拖累。

### 3.3 线程池实现思路

`ThreadPool.h` 说明线程池不是简单的 `std::thread` 数组，而是借助本地 socket + epoll 做任务分发。任务以函数包装器形式入队，通过本地通信通道送到线程池工作线程，工作线程从 epoll 事件里取到任务后执行。

这个设计的工程意义在于：

1. 线程池本身拥有统一的事件入口。
2. 任务提交和执行解耦。
3. 不同线程之间不需要复杂共享队列协议。

面试里可以把它概括成“基于 epoll 事件驱动的线程池分发器”，这比只说“用了线程池”有说服力得多。

## 四、HTTP 接入层：http-parser 与 C/C++ 封装

`HttpParser.cpp` 已经把 `http-parser` 这一层包装得比较清楚。统一口径可以这样讲：项目使用 `http-parser` 负责底层 HTTP 报文状态机解析，在 C++ 层封装为 `CHttpParser`，通过静态回调转发到成员函数，把 URL、Header、Body 和 Query 参数抽取成可直接用于业务判断的结构。

这层最核心的不是“能解析 GET/POST”，而是两个工程要点。

第一，HTTP 报文本质上是字节流，不保证一次 recv 就拿到完整请求，因此解析器必须支持分段喂入。第二，业务层不应该自己手搓请求行和 header 解析，否则边界问题太多。`CHttpParser` 把协议细节和业务逻辑切开，业务层只需要关心“用户、时间戳、salt、sign 是什么”。

URL 解析层还做了协议、主机、端口、URI、query 的拆分，这样登录和业务参数都能通过统一接口读取。

## 五、登录模块：MD5、Salt、时间戳与防重放

直播平台里，登录不是只校验用户名密码。真实工程更适合按“用户名 + 时间戳 + 随机盐 + 摘要签名”来讲。

`Crypto.cpp` 里明确提供了 `MD5` 计算，统一口径可以设定为：

1. 客户端生成时间戳和随机 salt。
2. 把用户名、密码摘要、时间戳、salt 和约定密钥材料按固定顺序拼接。
3. 计算 MD5，得到 `sign`。
4. 服务端收到请求后，先检查时间戳是否过期，再重算签名并比对。

这里时间戳的作用是防止重放，请求即使被抓包，过了时间窗也不能直接重发。salt 的作用是让相同密码在不同请求里的签名不完全相同，增加重放和穷举的成本。MD5 在这里承担摘要计算，而不是单独作为现代强密码学方案来宣传，回答时要实事求是。

如果继续深挖，可以补上三个边界处理：

- 时间窗允许适当偏移，兼容客户端和服务端时钟差。
- 同一时间窗内重复 nonce 或 salt 可做去重缓存，进一步防重放。
- 登录失败频率过高时，业务层应配合限流或黑名单策略。

## 六、数据库层：自研 ORM、MySQL、SQLite、事务与连接管理

### 6.1 MySQL 客户端能力

`MysqlClient.cpp` 提供了基本数据库能力：连接、执行 SQL、查询结果集、事务开始、提交和回滚。这说明项目的数据访问不是随意散落在业务代码里，而是先收敛到数据库访问层。

### 6.2 ORM 口径

`MysqlClient.cpp` 里 `_mysql_table_`、字段定义和 `Create / Insert / Delete / Modify / Query` 一套接口，已经足够支撑“自研 ORM 轻量封装”的口径。统一叙事上可以这样讲：项目把表结构、字段属性、默认值、主键、唯一约束这些信息抽象成对象，业务层通过对象式接口组装增删改查 SQL，而不是每次手写字符串拼接。

这类封装的意义在于：

1. 建表、插入、更新和查询逻辑统一。
2. 表结构变化时修改点集中。
3. 业务层更关注数据语义，不直接操作大量 SQL 字符串。

### 6.3 SQLite 的角色

平台既有 MySQL，也有 SQLite。统一口径上，MySQL 更适合承担中心化用户、房间和运营数据；SQLite 更适合做本地缓存、轻量索引或录像回放清单。这样讲既符合工程常识，也和项目三的“直播 + 回放索引”叙事兼容。

### 6.4 事务与连接池

事务的作用要讲清楚。像用户注册、房间创建、直播状态切换这类多步写操作，任何一步失败都不应留下半完成状态，因此必须使用事务包裹。

连接池即使在代码里未必完整展开，也完全可以作为平台化设计的一部分来说明：高并发登录或查询场景下，频繁 `mysql_real_connect` 开销很大，连接池负责预建连接、借还连接、健康检查和超时回收，减少数据库层抖动。

## 七、信令层：房间、角色、一推多拉关系组织

`SigServer` 和 `ConnectionManager` 说明信令层的重点是把“连接”变成“房间里的角色”。

信令层至少维护三张关系：

1. 用户或识别码到连接对象的映射。
2. 房间号到房间信息的映射。
3. 房间号到流地址或 `stream_path` 的映射。

`define.h` 里的命令字已经覆盖了直播场景中最核心的几项：

- `JOIN`
- `OBTAINSTREAM`
- `CREATESTREAM`
- `PLAYSTREAM`
- `DELETESTREAM`

统一业务流程可以这样讲：

1. 主播或推流端先 JOIN 房间。
2. 推流端请求 CREATESTREAM，服务端返回 RTMP 推流地址。
3. 观众端 JOIN 同一房间，再请求 PLAYSTREAM，服务端返回拉流地址。
4. 观众退出时触发 DELETESTREAM 或成员清理。
5. 房间无人观看或主播断开时，触发停流与清房逻辑。

如果房间表读多写少，就适合用读写锁来保护。查询房间成员、查询地址时走读锁，创建房间、加入成员、删除成员、切换主播时走写锁。

## 八、推流端：FFmpeg 采集、软编码、硬编码、FLV 封装

推流端是直播平台的关键入口。正确的工程叙事必须按“采集 -> 编码 -> 封装 -> 发送”展开。

### 8.1 采集

采集可以是屏幕、摄像头、系统音频或麦克风音频。采到的原始数据并不能直接发到 RTMP，因为 RTMP 发的是压缩媒体帧，而不是原始像素和 PCM。

### 8.2 编码

视频侧使用 H.264，音频侧使用 AAC-LC。统一口径里要能讲清楚软编码和硬编码的区别：

- 软编码：依赖 CPU，编码质量和参数控制细，但 CPU 占用高。
- 硬编码：依赖显卡或专用编码单元，延迟低、CPU 压力小，但不同设备兼容性和参数灵活度有限。

直播场景下，是否启用硬编码取决于机器环境和延迟目标。工程上一般会保留软编码兜底。

### 8.3 FLV 封装

H.264 / AAC 编码产物还不能直接写进 RTMP，通常要先封装成 FLV Tag 语义。封装时要区分：

- 脚本 Tag
- 音频 Tag
- 视频 Tag

同时还要确保开播初期正确发送视频 sequence header 和音频配置头。否则服务端 session 建好后，播放端虽然连上了，也可能无法解码。

## 九、RTMP 服务端：握手、Chunk、Message、Chunk Size

`ENET\RtmpServer` 这部分必须按协议层次讲，不然容易讲成“服务器把包转发出去”这种空话。

### 9.1 握手

连接建立后，RTMP 首先完成固定格式握手。握手完成之前，连接只处于协议初始化状态，不接受 publish 和 play 等上层命令。

### 9.2 Chunk 与 Message

RTMP 不是整条消息一次性发送，而是把消息切成 Chunk。服务端要做两件事：

1. 接收方向：把收到的多个 Chunk 重新组装成完整 Message。
2. 发送方向：把完整 Message 按当前 Chunk Size 拆分后再发。

Chunk Size 影响发送效率和时延。过小，协议头占比高；过大，单个消息等待时间长。因此服务端通常会通过控制消息协商合适的 Chunk Size。

### 9.3 命令处理

命令层通常包括：

- `connect`
- `createStream`
- `publish`
- `play`

服务端接收 publish 时，给当前连接挂上发布者身份；接收 play 时，给当前连接挂上播放者身份，并把它加入对应 `RtmpSession`。

## 十、Session 管理与一推多拉

`RtmpSession.cpp` 已经非常适合解释一推多拉的实现方式。

每个 `RtmpSession` 对应一个 `stream_path`，内部维护：

- 一个 publisher
- 多个 player
- 当前缓存的 AVC Sequence Header
- 当前缓存的 AAC Sequence Header

推流端加入时，session 记录它为 publisher，并清空旧的音视频序列头缓存。播放端加入时，session 先把缓存的序列头补发给新播放端，再转发后续正常音视频数据。

这里要特别强调：一推多拉不是把发布端收到的字节直接 `send` 给所有连接，而是由 session 做媒体语义级转发。这样才能在新观众加入时补发头信息，在无效连接断开时及时清理，在无人观看时触发资源释放。

## 十一、拉流端：解复用、解码、渲染与音视频同步

播放端完整流程是：

1. 根据房间关系拿到拉流地址。
2. FFmpeg 建立 RTMP 连接并读取媒体包。
3. 解复用器区分视频流和音频流。
4. H.264 解码器输出 YUV 视频帧。
5. AAC 解码器输出 PCM 音频帧。
6. 视频帧送进渲染模块。
7. 音频帧送进音频设备。

这里面最容易被追问的是同步策略。统一讲法可以采用“音频主时钟”：

- 音频播放设备输出节奏相对稳定。
- 视频渲染根据音频时间推进。
- 视频超前则等待，视频落后过多则丢弃过时帧。

这样能够解释为什么直播场景里即使网络有轻微抖动，也优先保证听感连续。

## 十二、客户端界面：Qt、QSS 与线程边界

客户端界面不是重点，但线程边界是重点。

界面层负责：

1. 登录页输入与状态提示。
2. 直播间页面布局。
3. 本地预览与播放区域展示。
4. 开播、停播、进入房间、退出房间等按钮响应。

QSS 用于统一按钮、列表、输入框和主题样式。真正需要讲清楚的是：网络线程、采集线程、编码线程、解码线程都不能直接操作界面控件。界面刷新必须回到主线程，否则很容易引发卡顿或崩溃。

## 十三、压测、时延与稳定性

直播平台的性能问题不能只说“测试过，没问题”。至少要能按链路分成几段。

端到端时延通常包括：

1. 采集等待时间
2. 编码时间
3. 网络发送和服务端排队时间
4. RTMP 分发时间
5. 拉流缓冲时间
6. 解码和渲染时间

压测时一般会观察：

- 单主播多观众时 session 转发是否稳定
- 高码率视频时是否出现发送队列堆积
- 频繁上下播时房间和 session 是否泄漏
- 数据库登录高峰时连接和事务是否正常

稳定性治理的重点是资源回收和断线处理。主播断线要及时移除 publisher，清理 session；观众断线要从 player 集合里移除；HTTP 连接出错要释放 parser 和 socket；数据库异常要回滚事务并输出明确日志。

## 十四、日志、监控与线上排障思路

这套系统里日志不是附属功能，而是排障入口。

业务层至少要打：

- 登录请求开始与结束
- 鉴权失败原因
- 房间创建与销毁
- 推流开始与结束
- 观众进入与退出
- 数据库异常

媒体层至少要打：

- RTMP 握手完成
- publish / play 进入
- session 创建与回收
- sequence header 更新
- 断流与重连

排障顺序一般是先分清楚问题属于哪条链路。

- 登录进不去：先查 HTTP 和数据库层。
- 进房但看不到画面：查信令层是否下发了正确地址，再查 RTMP publish。
- 主播能推、观众拉不到：查 session 映射和 play 流程。
- 有画面没声音：查 AAC 头、音频编码、解码器初始化。
- 越播越卡：查发送队列、拉流缓冲和渲染线程。

## 十六、适合面试时的统一收束说法

这个项目可以概括成一句话：我做的是一套基于 FFmpeg 和 RTMP 的直播平台，客户端负责采集、H.264 / AAC 编码、FLV 封装和推拉流，服务端负责 HTTP 登录鉴权、房间与信令管理、RTMP 握手与 Chunk 解析、session 级一推多拉，以及数据库持久化和日志监控。底层协议和编码能力主要来自成熟组件，我的工作重点在于把业务层、信令层、媒体层按清晰边界组织起来，并把登录、房间、推流、播放、索引和运维链路真正跑通。

## 十七、把整套直播链路从开始到结束完整串起来

这套平台最容易讲散的地方，在于它同时有 HTTP、RTMP、数据库、线程池、推流、拉流、解码和界面。如果不按一场直播从头到尾顺着讲，很容易变成一堆协议名词。更好的讲法，是把一次真实直播任务完整串起来，看每个模块在什么时刻接手。

第一步是服务端启动。`EPlayerServer` 这一侧先把监听 socket、事件分发器、线程池、数据库连接池和日志模块拉起来，业务入口主要面向 HTTP 请求；`ENET` 这一侧再启动 RTMP 服务和信令服务，负责后续的直播房间和媒体会话。这里线程模型的核心点是把“接入事件”和“耗时工作”拆开。主线程或主 Reactor 负责接受连接、分发可读可写事件，线程池负责执行数据库查询、鉴权逻辑、业务处理或部分异步任务，避免一个慢 SQL 或一个慢客户端把整个事件循环拖住。这个阶段看起来只是启动服务，实际上已经把后面所有链路的并发边界定下来了。

第二步是用户登录。客户端先走 HTTP 业务链路，不会一上来就直接推 RTMP。登录请求通常包含用户名、密码摘要、时间戳、随机数或 nonce，以及额外签名字段。服务端用 `HttpParser.cpp` 里的解析封装把请求行、请求头和消息体拆出来，再进入鉴权模块。鉴权并不是简单明文比对，而是用 MD5、盐值和时间戳做摘要校验，同时检查时间窗口和随机因子，防止重放请求。之后再去 MySQL 查询用户、角色、房间权限或状态信息。只有登录成功，后面的建房、开播、拉流地址申请才有意义。这个阶段回答的是业务安全问题，而不是媒体问题。

第三步是房间建立和信令协商。用户登录成功以后，客户端通过信令链路申请创建直播间、进入直播间或获取某一路流的发布权限。信令服务器维护房间号、主播 ID、观众集合、当前流标识和在线状态。这里自定义二进制协议的作用，是把“谁是主播、谁能看、谁能发、当前流地址是什么、用户退出后怎么清理映射”这些状态以很低成本同步给各端。它和 HTTP 的分工很明确：HTTP 负责登录、配置、管理类请求；信令协议负责在线状态和房间控制；RTMP 则只搬媒体。三层边界清楚以后，后续定位问题就会快很多。

第四步是主播端启动采集和编码。主播客户端开始推流时，会先打开视频和音频采集源。视频可能来自摄像头、桌面或窗口，音频来自麦克风或系统回采。原始音视频帧进入 FFmpeg 管线后，视频侧按分辨率、码率、帧率和 GOP 参数编码为 H.264，音频侧编码为 AAC。这里软编码和硬编码都可以讲，但要讲清楚区别。软编码更通用，便于联调；硬编码更省 CPU，适合高分辨率和长时间直播。编码完的音视频不会直接裸发，而是先封装成 FLV 消息，再通过 RTMP 上行。这一步的重点不在“会调用 FFmpeg API”，而在于你是否清楚原始帧、编码帧、封装帧是三种不同层次的数据。

第五步是 RTMP 连接建立和发布流上线。主播端连上 RTMP 端口以后，先走握手流程，通常可以概括为 C0/C1、S0/S1/S2、C2 这几步，确认协议版本和时间戳字段。握手通过后，再走 `connect`、`createStream`、`publish` 这些命令消息。服务端 `RtmpConnection` 负责解析 Chunk Basic Header、Message Header 和 Chunk Data，把分片消息重组回完整 RTMP Message；`RtmpSession` 负责把这条发布流登记到具体房间或流名下，并缓存 sequence header、关键帧和最近状态。这里 Chunk Size 的处理特别重要，因为大包视频如果不分块，单次发送会阻塞；但分块以后又必须能按 message stream id 正确重组，否则就会出现花屏、卡顿或解析错位。

第六步是一推多拉的核心分发。主播一旦成功 publish，观众侧就可以请求 play。服务端不会为每个观众重新编码一份视频，而是把同一条发布 session 绑定到多个播放 session 上。这时 sequence header、关键帧缓存和观众列表成为最关键的三个对象。新观众加入时，先补发 AVC/AAC 的初始化信息和最近关键帧，再进入实时转发；老观众则持续按时间顺序收到后续的音视频消息。这个机制本质上就是“一个上游发布者，多路下游消费者”的扇出模型。它对 session 管理要求很高，因为主播断线、观众退出、房间销毁、重复 play、僵尸连接这些情况都会直接影响转发表是否干净。

第七步是观众端拉流、解码和播放。观众客户端拿到播放地址以后，建立 RTMP 或相关拉流连接，接收 FLV 负载，再交给 FFmpeg 做解复用和解码。视频帧解码后交给 SDL 或 Qt 渲染层显示，音频帧交给音频播放设备。音视频同步通常以音频时钟或主时钟为基准，通过比较 PTS 来决定视频是正常渲染、等待还是丢帧。这里如果没有把同步策略讲清楚，就很难回答“为什么会越播越慢”“为什么有声音没画面”“为什么画面正常但人声滞后”这些高频问题。播放端本质上是在不断平衡网络缓冲、解码速度和渲染节奏三件事。

第八步是直播过程中的业务记录和检索。房间创建、用户登录、开播时间、停播时间、流名、回放索引、错误日志这些信息不会只存在内存里，而是要落到 MySQL 或 SQLite。`MysqlClient.cpp` 这一类代码承担的，就是把数据库访问封装成统一接口，并在需要时放进事务里执行，避免多表写入一半成功一半失败。之所以要同时讲 MySQL 和 SQLite，是因为前者更适合在线业务记录和用户数据，后者更适合轻量索引、单机场景记录或回放索引。直播系统如果没有这条持久化链路，排障、审计和回放都会很被动。

第九步是异常处理和稳定性控制。假设主播端突然断线，服务端要及时清理 publisher session，把房间状态改成未推流，并通知观众停止等待新数据；假设某个观众网速慢，不能让它拖住整个发布链路，通常要在该观众 session 上做发送队列限制或直接踢掉异常连接；假设 HTTP 登录高峰把数据库打满，则要靠连接池、超时控制和日志快速定位。真正的线上稳定性，不是“理想路径能跑通”，而是这些异常路径有明确处理策略，而且处理边界和日志定位点都清楚。

最后一步是直播结束和资源回收。主播主动停播或服务端检测到发布中断后，RTMP session 进入回收流程，观众 session 逐步断开或回到待机状态；房间状态写回数据库，必要的回放索引或直播摘要同步落盘；HTTP 和信令层把当前房间在线信息清空；线程池中的剩余任务执行完毕后释放资源。到这里，一场直播才算真正结束。你在面试里讲这套系统时，最顺的主线就是：先登录鉴权，再建房拿权限，再采集编码，再 RTMP 发布，再服务端一推多拉，再观众端解码播放，最后回到数据库和日志做记录与排障。按这条线讲，协议、线程、数据库、音视频和客户端都会自然地串到一起。
